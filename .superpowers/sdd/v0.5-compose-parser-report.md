**Naming deviation from the brief, unavoidable:** the brief's sketch has both `func Plan(...)` and `type Plan struct{...}` — a function and a type can't share one identifier in Go. I kept the noun `Plan` as the type name (it matches `ServicePlan`/`PlanContext`) and named the function `BuildPlan`. Task 8 must call `compose.BuildPlan(...)`, not `compose.Plan(...)`.

```go
type File struct {
    Project      string             // top-level `name:`, "" if unset
    Services     map[string]*Service
    ServiceOrder []string           // YAML document order, for determinism
    Volumes      []string           // top-level `volumes:` names declared
    Warnings     []string           // file-scoped only; a service's own warnings are on Service.Warnings
}

type Service struct {
    Name        string
    Image       string
    Build       *BuildRef
    Environment map[string]string
    Expose      []int      // raw expose list, in order; empty = internal service
    Volumes     []VolumeRef
    DependsOn   []string
    Warnings    []string
}

type BuildRef struct {
    Context    string // never empty; defaults to "." for the mapping form
    Dockerfile string
    Args       map[string]string
}

type VolumeRef struct {
    Name   string // named volume name (never a host path — bind mounts are a Parse error)
    Target string // container mount path
}

type ServiceKey struct { Project, Service string }

type ExistingApp struct { Slug, Alias string }

// PlanContext is built by the caller from internal/store; this package
// never imports store.
type PlanContext struct {
    ExistingApps map[ServiceKey]ExistingApp // this project's apps from a prior compose apply
    TakenAliases map[string]string          // every claimed network alias -> human-readable owner description
}

type Plan struct {
    Project  string
    Services []ServicePlan // topological deploy order; orchestrator deploys sequentially, stop-on-first-failure
    Warnings []string       // file-scoped only
}

type ServicePlan struct {
    Name, Slug, Image   string
    Build                *BuildRef
    Port                 int    // 0 when Internal
    Internal             bool   // true = no Caddy route, no probe target
    Env                  map[string]string
    Volumes               []VolumeRef
    DependsOn             []string  // informational; Plan.Services is already ordered
    Alias                 string    // == Name; the bare network alias Task 8 must apply alongside app-<slug>
    Action                string    // "create" | "update"
    RecommendedStrategy   string    // "" or "replace" — set whenever Volumes is non-empty
    StrategyReason        string    // human-readable reason, "" when RecommendedStrategy is ""
    Warnings               []string // this service's own warnings, carried from Parse
}
```

### Wiring notes for Task 8

- Build `PlanContext.ExistingApps` from the store: for every app already tagged with this compose project (`compose_project`/`compose_service` columns from Task 8's own migration 00009), key it `ServiceKey{Project: project, Service: compose_service}` -> `ExistingApp{Slug: app.Slug, Alias: <its current bare-name alias, if any>}`.
- Build `PlanContext.TakenAliases` from every alias currently claimed on the shared network: other compose projects' services (their bare service-name alias) plus every hand-created app's `app-<slug>` alias if that scheme also claims bare names (check current alias scheme in `internal/deploy`). A project's own prior aliases should also appear here mapped to a description — `BuildPlan` recognizes the self-owned case via `ExistingApps`, not by string-matching the description, so it's safe (and expected) to include them.
- `ServicePlan.Alias` is always `== Name`; apply it as an extra network alias alongside the existing `app-<slug>` alias when creating/updating the container.
- `ServicePlan.RecommendedStrategy == "replace"` should be applied by Task 8 as the app's `deploy_strategy` (Task 6's column) — this package only recommends, it never touches a store.
- `ServicePlan.Env` and `.Volumes` are always non-nil (empty slice/map, not nil) for a service with none.
- Re-applying the same compose file is idempotent as long as Task 8 populates `PlanContext` correctly: `Action` flips to `"update"` and `Slug` is taken from the store's `ExistingApp.Slug` rather than re-derived.

## Compose keys: supported vs. warn vs. error

**Parsed (documented subset):**
- `services.<name>.image` (string)
- `build`: bare string (context) or mapping `{context, dockerfile, args}` (args as a mapping; args as a list warns+skips)
- `environment`: map form (values coerced from string/bool/int/float; `null` warns, treated as empty) and list form (`K=V`; bare `K` with no `=` warns, treated as empty)
- `volumes` (service-level): short syntax `name:/path[:mode]` and long syntax `{type: volume, source, target}` — **named volumes only**
- `depends_on`: list form (supported); map/long form with `condition:` accepted but warns ("only ordering is honored")
- `expose`: list of ports/strings (optional `/tcp` suffix stripped); more than one entry warns naming the extras, first one wins
- top-level `name` (project — informational; `BuildPlan` takes its own `project` argument)
- top-level `volumes:` — declared names cross-checked against service usage (see below)

**Warn (never silently dropped), by name:**
- `ports` (host publishing) — "routing happens via Caddy through 'expose' or a domain"
- any other unrecognized service key: `restart`, `command`, `networks`, `deploy`, `healthcheck`, `profiles`, `extends`, `cap_add`, `entrypoint`, `labels`, etc. — `unsupported key %q (ignored)`, per service
- any unrecognized top-level key — `unknown top-level field: %s`
- `build.args` as a list instead of a mapping
- unrecognized `build.*` sub-keys (e.g. `target`, `cache_from`)
- anonymous volume mount (`- /data` with no source)
- long-form volume with `type:` other than `volume`/`bind` (e.g. `tmpfs`)
- volume mount mode segment (`:ro`/`:rw`) — accepted but not enforced
- a named volume used by a service but not declared in top-level `volumes:` (only checked when the top-level `volumes:` key is present at all)
- a top-level `volumes:` entry declared but never used by any service
- `version:` (legacy compose marker) is the one deliberate silent exception — carries no translatable info, would just be noise

**Hard errors:**
- bind mount (host path on either side of a volume — `./data:/data`, `/etc:/etc`, long-form `type: bind`) — names the service and the mount string
- a service with neither `image` nor `build`
- malformed YAML / wrong type for any recognized field (each names the field and what it got)
- a service or top-level `services:`/`volumes:` value of the wrong YAML kind
- duplicate service name (defensive; unusual to hit via normal YAML)
- (Plan-time) invalid project name, invalid/reserved service name, slug too long or reserved, alias collision, undefined `depends_on` target, `depends_on` cycle

## Concerns / design calls made where the brief was silent or self-contradictory

1. **`Plan`/`BuildPlan` naming collision** (above) — the brief's interface sketch isn't literal Go. Flagging clearly so Task 8's brief (not yet written) names the function correctly.
2. **Where "expose extra ports" and "internal/expose split" get decided:** I resolved the extras-ignored warning at **Parse** time (intrinsic to the file, no project context needed) and the Port/Internal split at **Plan** time (matches the brief's test-matrix placement: "expose/internal split" is listed under Plan's tests). `ServicePlan.Port`/`.Internal` only exist on the Plan side.
3. **Top-level `volumes:` cross-check semantics** — the brief says names are "validated against services' usage" but doesn't specify error vs. warning. I made both directions **warnings**, not errors: a service volume not declared at top level warns (many real compose files omit the top-level section entirely, and being lenient there avoids over-rejecting valid files); a declared-but-unused top-level volume also warns. If the cross-check is present at all it only activates when the top-level `volumes:` key exists in the document.
4. **Volume mount `:ro`/`:rw` mode** — accepted but always warned as "not enforced" rather than silently accepted or rejected, since BasePod doesn't currently support read-only volume mounts and silently dropping the `ro` guarantee felt worth flagging under the "nothing silently dropped" philosophy, even though it's a mount modifier rather than a top-level key.
5. **The outer task prompt vs. the brief disagree on `restart`/`command`/`ports`:** the outer prompt's paraphrase lists `ports`/`expose`/`restart`/`command` as "supported subset" members; the brief (marked authoritative) treats `restart` and `command` as unsupported-warn like any other unrecognized key, and `ports` as warn-only (never parsed into anything). I followed the brief. Worth a sanity check with whoever wrote the outer prompt if `restart`/`command` were actually meant to be parsed into something (e.g. a container command override) — nothing in Plan/ServicePlan currently carries a command field.
6. **Project name normalization** — `BuildPlan` lowercases and space-replaces the `project` argument the same way `apps.go`'s `slugify` does, then validates it as a slug-component shape. It does not consult `File.Project` (the compose file's own `name:`) at all — precedence between a caller-supplied project name and the file's `name:` is left entirely to Task 8, as the interface signature implies (`project` is a required argument, not derived).
7. **Untouched packages, as instructed:** no changes to `internal/store`, `internal/api`, or `internal/deploy` — this task is `internal/compose/**` only, confirmed by `git status` before commit (two new files only).
8. **Not yet exercised end-to-end:** this package has zero runtime wiring (no HTTP route, no CLI verb) — by design, since Task 8 owns the apply endpoint/orchestration and Task 10 owns the UI. `go test ./... -count=1` is green across the whole repo, but that only proves this package doesn't break anything existing, not that Task 8's eventual integration will be friction-free against the exact `PlanContext` shape assumed above.
