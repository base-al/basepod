## The icon diagnosis (what was actually wrong)

This is a plain Vite + Vue SPA using `@nuxt/ui`'s Vite integration (not full Nuxt). `@nuxt/ui`'s `<Icon>` component resolves `i-lucide-settings` → `@iconify/vue`'s `<Icon icon="lucide-settings">`. `@iconify/vue` only renders offline if the icon's SVG data has already been registered locally (via `addIcon`); otherwise it fetches from `https://api.iconify.design` at runtime with no offline fallback and no visible error on failure.

`@nuxt/ui`'s Vite plugin *can* pre-bundle icons offline at build time (`icon.clientBundle.scan`, mirroring `@nuxt/icon`'s option), but **this is opt-in and was never enabled** — confirmed by reading `node_modules/@nuxt/ui/dist/unplugin.mjs`: without `clientBundle.scan`, the file-scanner never runs, `scannedIcons` stays empty, and only Nuxt UI's own internal default icons get bundled — none of this app's `icon="i-lucide-*"` usages. Grepping the pre-fix `dist/assets/*.js` confirmed it: no `addIcon`/bundle-init code anywhere, but a literal `api.iconify.design` string in the router chunk — every icon in the app depended on an uncached third-party network call. That explains the invisible gear exactly: any icon whose fetch didn't win the race (or was blocked — ad blockers commonly block iconify.design, and this is a self-hosted ops tool that may run behind restrictive networks) silently renders nothing, with an icon-only button then showing literally nothing.

**Fix:** `web/vite.config.ts` now passes `icon: { clientBundle: { scan: true } }` to the `@nuxt/ui/vite` plugin. Rebuilt and grepped `dist/assets/*.js`: every icon name referenced anywhere in `src/**/*.vue` (31 distinct `i-lucide-*` names, cross-checked with a diff script) now has its SVG body inlined directly in the JS bundle — zero runtime network dependency. Verified end-to-end by building the real Go binary, serving it, and confirming the fetched `/assets/index-*.js` byte-for-byte matches the local build and contains the icon bodies for icons still in use (settings' own icon key is no longer emitted because the redesign replaced the icon-only Settings button with a plain text nav link — see below).

**Audit of every icon in the app:** every `icon="i-lucide-*"` prop currently in the codebase resolves to a valid `@iconify-json/lucide` entry (2 — `alert-circle`/`alert-triangle` — resolve via lucide's own alias table to `circle-alert`/`triangle-alert`; `history` resolves via alias to `rotate-ccw-clock`; the earlier agent's suspicion about `i-lucide-history` was unfounded — it renders fine, alias resolution works correctly through `resolveBundleIcons`). Every icon-only (`square`) button in the app already carries `aria-label` (`AppShell`'s theme toggle, `NewApp`'s back button, `EnvEditor`'s and `DomainsPanel`'s trash/external-link/copy buttons — 8 total, all covered). Every other icon usage is paired with visible button text.

**Belt-and-suspenders on the specific bug:** rather than just fixing the icon and keeping an icon-only Settings button, `AppShell.vue`'s primary nav (Apps, Settings) is plain text — no icon at all for the two most safety-critical destinations, so a future icon regression structurally cannot hide navigation again.

## What was missing from the API (reported, not worked around)

- **App's public URL in the apps list.** The generated hostname (`<slug>.<root_domain>`) requires `root_domain`, which is exposed **only** via `GET /apps/{slug}/domains` (`internal/api/domains.go`) — confirmed by grep and by live testing (`GET /apps/verify-alpha/domains` → `{"generated":"verify-alpha.apps.localhost",...}`). `GET /system` (`internal/api/system.go`) has only `version`/`podman`/`apps`, no `root_domain`. `GET /apps` (the list endpoint) returns `App[]`, which has no domain field at all. Showing the URL in the list would require one extra request per app (N+1), which this pass was told to avoid, or a Go change to add `root_domain` to `/system` or the app-list payload — which this pass was told not to make. **Left out of the list**; `AppDetail.vue` already shows it via its own single per-app fetch, unchanged.
- **Last-deployment info in the list.** `GET /apps` returns `App[]`, not `AppDetail[]` — no `deployments` field. Only `GET /apps/{slug}` (already one-per-app) carries deployment history. Left out for the same N+1 reason.

Neither blocked the work — both are cleanly reportable gaps, not missing fields that stopped the page from functioning. **No Go code was touched.**
