## What was built

**Task 4** — `internal/api/git.go` (new): `PUT/GET/DELETE /api/v1/apps/{slug}/git`,
`GET /api/v1/apps/{slug}/git/deliveries`, `POST /api/v1/apps/{slug}/deploy/git`.
Hook ID + webhook secret minted on first connect, stable across a re-PUT,
rotated only on `{"rotate_secret":true}`. Secret returned in plaintext on
GET (per plan — operator has to paste it into a forge); deploy token is
write-only, masked to `"set"`/`""`. Both sealed with AAD bound to
`(appID, "git_secret")` / `(appID, "git_token")` via the existing
`seal`/`open` closures. Manual deploy clones synchronously (so connection
problems surface as an immediate 502/503 while testing) then hands off to
a new `deploy.Engine.DeployGitAsync`, which mirrors `DeployBuildAsync` but
records `source="git"` and the resolved commit on `deployments.git_sha`.

**Task 5** — `internal/api/webhook.go` (new): `POST /api/v1/webhooks/git/{hookID}`,
the only unauthenticated route. Constant-time signature verification
(`hmac.Equal` / `subtle.ConstantTimeCompare`) for GitHub
(`X-Hub-Signature-256`), Gitea (`X-Gitea-Signature`, also accepts GitHub's
header), and GitLab (`X-Gitlab-Token`). An unknown `hook_id` and a known
hook's bad/missing signature return an identical 401 response (status,
body, error code, and headers) — deliberately not the 404-vs-401 split the
plan doc sketched, since that split is itself an oracle for whether a
`hook_id` was ever valid; see "Deviations" below. 1 MiB body cap via its
own `http.MaxBytesReader`. Branch filter (`ignored_branch`), ping
(`ignored_event`), branch-deletion push (all-zero `after`, `ignored_event`),
non-push events (`ignored_event`). Per-hook rate limit (30/min, reusing the
existing `rateLimiter`). Per-app flood coalescing (`gitCoalescer`, new
type in `git.go`): at most one deploy running plus one queued per app,
newest commit always winning, every coalesced push still recorded as its
own delivery. The clone itself runs in the background — a new
`deploy.Engine.DeployGitCloneAsync` (fetch closure deferred into the
goroutine, `onDone` callback releases the coalescer slot and chains a
queued follow-up) — so a webhook response never blocks on a multi-minute
clone. URL/branch/token used for cloning come exclusively from the stored
`git_sources` row; the payload can only trigger/filter, never steer.

**Store** (`internal/store/store.go`): `Deployment.GitSha` field +
`deployments.git_sha` wired into `deploymentColumns`/`scanDeploymentRow`
(the column already existed from migration 00007 — Task 2 — I did not add
a new migration, per the plan's ownership rule); `SetDeploymentGitSHA`,
`DeploymentByID`, `UpdateGitDeliveryStatus` (new methods, all additive,
no schema change).

**Deploy engine** (`internal/deploy/deploy.go`): `DeployGitAsync` (sync
clone, already-prepared build context — manual trigger) and
`DeployGitCloneAsync` (fetch closure runs in the background goroutine —
webhook trigger), both sharing a new `createGitDeployment` helper mirroring
`createBuildDeployment`.

**CLI**: `basepod git connect|status|disconnect`, `basepod deploy --git`
(`internal/cli/client.go` + `commands.go`).

**Server wiring** (`internal/server/server.go`): constructs a
`gitsource.Cloner` unconditionally (gracefully degraded, not nil, when git
isn't installed) and threads it into `api.New` as the new `GitFetcher` arg.

## Deviation from the plan doc, called out explicitly

The milestone plan (`docs/superpowers/plans/2026-08-06-v0.5-git-compose-teams.md`,
Task 5) sketches: "unknown/malformed hookID → generic 404 `not_found`...
Invalid [signature] → 401 `invalid_signature`". Taken literally, that's a
404-vs-401 split — which is itself an oracle for whether a `hook_id` is
real, undermining `GitSourceByHookID`'s own doc comment ("no oracle for
whether a hook ID was ever valid"). I implemented the property the
orchestrating task description explicitly called for instead: unknown
hook and bad signature return the **same** 401 response, verified by
`TestWebhookUnknownHookIndistinguishableFromBadSignature`. Flagging this
so it's a conscious call, not a silent drift from the plan doc — worth a
one-line note in doc 06's refresh (Task 12) if that hasn't already
accounted for it.

## Concerns

1. **The plan-doc deviation above** — please confirm the
   indistinguishable-401 design is what's wanted before Task 12 writes it
   into doc 06 as "delivered."
2. **`-race` runtime on this package is long** (~15 min) purely because of
   argon2 in the login path, unrelated to anything I added — every test
   that calls `login()` pays that cost under race instrumentation. Not a
   new problem (pre-existing in the suite), but worth knowing before
   anyone else's CI/local gate trips a shorter timeout on it.
3. **Coalescing is per-process, in-memory** (`gitCoalescer`, keyed by app
   ID) — fine for BasePod's single-daemon architecture today, but doesn't
   survive a restart mid-flood (a queued-but-not-yet-started pending push
   is simply lost, not deployed) or generalize to a future multi-instance
   deployment. Matches the plan's own "small struct... per-app mutex map"
   design; flagging as a known limitation, not a bug.
4. **Manual deploy-from-git (`POST .../deploy/git`) has no concurrency
   guard of its own** — unlike the webhook path, two rapid manual triggers
   for the same app both clone+build concurrently (only the build
   pipeline's own per-app mutex in `internal/build.Builder` serializes the
   actual `podman build`, not the clone). Low risk (it's an authenticated,
   deliberate operator action, not adversarial input) but worth a look if
   it ever becomes user-visible as a race.
