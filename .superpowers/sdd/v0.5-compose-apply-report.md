## Request shape chosen, and why

`POST /api/v1/compose/up?project=<name>&dry_run=1|0`, body a **gzipped tar**
(`Content-Type: application/gzip`/`application/x-gzip`) carrying
`compose.yaml` (or `compose.yml`/`docker-compose.yml`) at its root, plus
zero or more services' own build-context subdirectories.

- A JSON envelope was rejected: it would force embedding a whole multi-file
  build context (or a base64 blob) inside JSON, mangling exactly the bytes a
  `build:` service's context needs byte-for-byte.
- A bare multipart form was rejected too: a tar is already the format
  `basepod compose up`/`basepod deploy` pack build contexts into, and
  gzip-tar-as-body is the convention `handleDeployTarball` already
  established for "upload a build context, get a deploy" — one convention,
  not two.
- `project` is a **query parameter**, not a form field, so a client never
  has to touch the tar itself to name the project; it falls back to the
  compose file's own top-level `name:` when omitted, and 422s only if
  neither is present (tested: `TestComposeProjectQueryOverridesFileName`).
- `dry_run=1` returns 200 with the full `Plan` translated into the same
  per-service JSON shape a real apply uses (so a client doesn't need two
  response schemas), touching nothing.

## Deployment numbers and partial failure — the key design decision

Every service's **deployment row is created synchronously**, in
dependency order, before the 202 response is ever written (via
`store.CreateDeploymentFull` directly — not through `Deployer`, which
always creates its own row). This is what lets the response report every
service's **real**, immediately-pollable deployment number, not a
prediction, and it's what makes the partial-failure contract precise: a
background goroutine (`runComposeOrchestration`) then walks the same
services in the same order and, on the first failure, finishes every
**remaining** (already-created, still-"deploying") row `failed` with
`"aborted: <service> failed"` — without ever calling the deployer for
them. Earlier successes are never rolled back. `DeployExisting`/
`DeployBuildExisting` (small, additive extractions of `Deploy`'s/
`DeployBuild`'s existing bodies, minus their own row-creation step) are
what let the orchestrator reuse those pre-created rows instead of Deploy/
DeployBuildAsync creating (and orphaning) a second one per service.

## Idempotence / orphans

Re-applying updates apps keyed by `(compose_project, compose_service)`
(`Action` from `compose.BuildPlan`) rather than duplicating. A service
removed from the file is **never deleted** — reported in the response's
`orphans` (slugs) and left running untouched; deleting a user's workload
as a side effect of an unrelated apply isn't acceptable, matching the
milestone's standing "never delete data without confirmation" stance.
Project-wide teardown is left to Task 10's dashboard (N individual
`DELETE /apps/{slug}` calls).

## Concerns

1. **Deployment-number/build-context coupling to the uploaded tar's
   lifetime.** The extracted upload directory (holding every service's
   build context) is only removed once the background orchestrator
   finishes (or immediately, for dry-run/early-error paths). A very long
   multi-service build chain keeps that temp directory alive for the
   whole `composeOrchestrationTimeout` (2h) if something hangs. Bounded,
   but worth knowing.
2. **Custom `build.dockerfile` naming.** `internal/build`'s pipeline only
   recognizes `Containerfile`/`Dockerfile` verbatim at a build context's
   root. Since this task must not modify `internal/build`, a compose
   service naming a custom Dockerfile (e.g. `Dockerfile.prod`) is
   accommodated by copying that file to `Containerfile` within the
   extracted context before packing — functional, but means the two
   packages have a small implicit coupling on that filename convention. If
   a future compose feature needs true multi-Dockerfile builds, this is
   the seam to revisit.
3. **Predicted vs. actual first-attempt semantics on `DeployExisting`
   failures.** If a service's `DeployExisting`/`DeployBuildExisting` call
   itself returns an error *after* internally mutating app/deployment
   state (mirroring `Deploy`'s own `fail()` path), that state is exactly
   what the real engine already produces for a normal deploy failure — no
   new inconsistency introduced, but it's worth a reviewer double-checking
   `deploy.go`'s two new methods against `Deploy`/`DeployBuild` line by
   line, since they're deliberately near-duplicates and any future change
   to one's body needs to be mirrored in the other (or refactored to share
   more).
4. **No end-to-end (real podman) test** for the internal-alias/no-route/
   no-probe path — covered at the unit level (`Routes()` skip,
   `runRollout`'s alias/probe-skip logic) but not exercised through a real
   container the way Task 12's e2e script is expected to. That script
   (not part of this task) is the natural place to close that gap.
5. I did **not** modify `internal/compose` — confirmed via `git status`
   before every commit — and treated its `BuildPlan` output as
   authoritative, including its documented `Plan`/`BuildPlan` naming
   deviation.
