## Libpod stats wire-format evidence

Verified two ways, per the brief's requirement, against a local podman
**6.0.1 client / 5.7.1 server** (`podman version`):

1. **Live daemon curl.** `curl --unix-socket <machine socket>
   http://d/v5.0.0/libpod/containers/bp-caddy/stats?stream=true` returns
   concatenated JSON objects shaped like Docker's classic stats API:
   `read`/`preread` timestamps, `cpu_stats`/`precpu_stats` (each with a
   nested `cpu_usage.total_usage`, `system_cpu_usage`, `online_cpus`),
   `memory_stats.usage`/`.limit`, `pids_stats.current`,
   `blkio_stats.io_service_bytes_recursive` (entries with `op`/`value`),
   and `networks` (map of interface → `rx_bytes`/`tx_bytes`/...). A
   captured two-sample stream showed ~5s between ticks.

2. **Podman source, same tag (v5.7.1), shallow-cloned and grepped
   locally** (`git clone --depth 1 --branch v5.7.1
   https://github.com/containers/podman.git`, since GitHub's code-search
   API returned empty results in this sandbox for reasons unclear — raw
   file fetches worked fine). Found the real chain in
   `pkg/api/server/register_containers.go`:
   `/libpod/containers/{name}/stats` routes to
   `compat.StatsContainer` — the **docker-compat handler**, not the
   libpod-native bulk one at `/libpod/containers/stats` (no `{name}`,
   backs `podman stats`, returns `[]define.ContainerStats` with fields
   like `CPU`/`MemUsage`/`MemLimit`/`PIDs` — the shape a naive reading of
   "libpod stats" would expect and initially the wrong rabbit hole I went
   down before finding the route registration). Because the request path
   is under `/libpod/...`, `compat.StatsContainer`'s `IsLibpodRequest`
   branch returns the struct "unconverted" — but unconverted here still
   means podman's own `compat.StatsJSON` (docker-shaped), never
   `define.ContainerStats`. Confirmed exact field names against
   `pkg/api/handlers/compat/types.go` and
   `vendor/github.com/docker/docker/api/types/container/stats.go` at the
   same tag. Also confirmed: `defaultStatsPeriod = 5 * time.Second`
   (`pkg/api/handlers/compat/containers_stats.go`) — matches the live
   capture — and that this per-name endpoint is marked **DEPRECATED** in
   podman's own swagger comments ("Please use /libpod/containers/stats
   instead"), though still fully functional on 5.7.1 and exactly what the
   milestone plan and task brief specify, so it's what this client uses.
   `libpod/stats_linux.go`'s `calculateCPUPercent` confirmed the CPU-%
   formula: `(cpuDelta/systemDelta) * 100`, i.e. 0-100 **per core**, not
   normalized by core count — `internal/podman/stats.go`'s
   `calcCPUPercent` additionally multiplies by `online_cpus` to match the
   standard `docker stats`/`podman stats` CLI convention instead (0-100
   summed across all cores in use), which is more legible for a dashboard
   sparkline than podman's raw per-core-only internal value.

Full doc-comment trail with all of the above lives in
`internal/podman/stats.go` above `Client.ContainerStats`.

## SSE payload shape (what the UI should expect)

`GET /api/v1/apps/{slug}/stats`, `event: stats`, one message roughly every
~5s (libpod's own sampling interval — not something BasePod controls),
JSON body:

```json
{
  "cpu_percent": 12.5,
  "mem_used_bytes": 41943040,
  "mem_limit_bytes": 536870912,
  "pids": 7,
  "net_rx_bytes": 10240,
  "net_tx_bytes": 4096,
  "block_read_bytes": 45178880,
  "block_write_bytes": 1200000
}
```

`cpu_percent` is 0-100 per core (a container fully using 2 cores reads
~200). This is BasePod's own stable shape
(`podman.ContainerStatsSample` / `internal/api/stats.go`'s
`statsEventPayload`) — never libpod's raw field names — so a future podman
upgrade changing wire shapes can't move the UI's contract. Net/block IO
are included since they "come free" from the same libpod sample, per the
brief.

Auth: `Authorization: Bearer <session-token>` OR
`?access_token=<stream-token minted with scope "stats" for this exact
slug>`. A session token in `?access_token=` is rejected, and a token
minted for `app_logs`/`build_log` cannot open this route (and vice
versa) — same pattern as the existing two SSE routes, extended per the
brief. Errors: 404 `app_not_found`, 409 `not_running`, 502 `stats_failed`,
503 `too_many_streams` (shared per-user/global cap with the other SSE
routes).

## Design notes / concerns

- **`api/embed.go` is a small addition beyond the brief's exact file
  list**, required by a hard Go constraint: `go:embed` patterns cannot
  reference a parent directory (verified directly — a
  `//go:embed ../../api/openapi.yaml` directive inside `internal/api`
  fails the build with `invalid pattern syntax`). Since the brief is
  explicit that `api/openapi.yaml` must live at the repo root (separate
  from `internal/api`), the embed directive has to live beside it; I
  added a one-file package `openapi` in `api/` (mirroring the existing
  `web/embed.go` pattern exactly, for the same reason: it can't embed
  `web/dist` from `internal/server` either) and `internal/api/openapi.go`
  imports it to serve the bytes — so `internal/api/openapi.go` is still
  the file that does the actual serving, as specified.
- The per-name stats endpoint (`/libpod/containers/{name}/stats`) is
  marked **deprecated** in podman's own source in favor of the bulk
  `/libpod/containers/stats?containers=...` endpoint. It's fully
  functional on the target 5.7.1 server and is what the milestone plan
  explicitly specifies, so I used it as directed — flagging this in case
  a future podman major version actually removes it, which would need a
  follow-up migration to the bulk endpoint (a bigger change: that
  endpoint returns one JSON object containing an array of per-container
  reports rather than one stream per container).
- `cpu_percent`'s scale (0-100 per core, so a 2-core-busy container reads
  ~200) is a deliberate choice matching `docker stats`/`podman stats`
  CLI convention rather than podman's own internal (0-100 *total*,
  uncorrected for core count) value — worth the UI/sparkline author
  double-checking this matches their axis-scaling assumptions.
- Compose, git, and webhook route handlers (owned by other v0.5 tasks)
  were read only for their request/response shapes to document them
  accurately in the OpenAPI spec — none of their `.go` files were
  modified.
- `go test ./... -count=1`'s per-package durations were all well under a
  minute except `internal/api` itself (27s without `-race`); no test
  timeouts or flakes observed across two full runs (once without `-race`,
  once with).
