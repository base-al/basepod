## What the API could NOT give this screen (reported, not worked around)

**Compose dry-run/apply response is missing per-service image, build
ref, volumes, and env keys.** The Task 10 brief and milestone plan both
describe per-service cards showing "image/build, port or internal,
volumes, env keys, action create/update." The actual wire shape —
`internal/api/compose.go`'s `composeServiceResponse`, returned by both
the dry-run and the real apply — only carries `name`, `slug`, `action`,
`internal`, `port`, `alias`, `deploy_strategy`, `deployment_number`, and
`warnings`. There is no field anywhere in the response for a service's
image, build context, declared volumes, or env var keys.

Per this task's scope (`web/**` only, no Go changes, "if an API field
you need is missing, STOP and report it rather than adding it"),
`ComposePreview.vue` renders every field the API actually returns —
name/slug, create-vs-update, internal-vs-port, the `replace` strategy
badge (with its "why" carried through `warnings`, which the Go side
already appends automatically), and both top-level and per-service
warnings — and does not fabricate image/build/volumes/env display. This
is called out in a code comment at the top of `ComposePreview.vue` too.
If per-service image/build/volumes/env visibility in the preview is
wanted, `composeServiceResponse` needs those fields added server-side.

## Deviation from the Task 9 brief's literal wording (intentional, matches the real API)

The brief says: *"The secret is shown once on creation; make that
explicit rather than implying it can be retrieved later."* The actual
shipped API contradicts this: `internal/api/git.go`'s
`gitSourceResponse` returns the webhook secret in **plaintext from every
GET**, not just on creation — its own doc comment calls this out as a
deliberate, self-reviewed deviation ("the operator must paste it into a
forge's webhook settings, possibly repeatedly"), and the milestone plan's
self-review section confirms it ("webhook secret is readable via GET").

`GitPanel.vue` follows the real, verified API rather than the brief's
original assumption: the secret is displayed with a copy button every
time the Git tab is open, with copy text reading "visible on this page
whenever you view it... treat this tab as sensitive" instead of a false
"shown once" claim.

## Screen descriptions

### Git tab (AppDetail.vue → "Git")

**Not connected:** a single card, "Connect a repo" — Repository URL
(must be `https://…`, inline validation), Branch (default hint `main`),
Access token (password input, optional, hint clarifies it's write-only
and required only for private repos). "Connect repo" button.

**Connected**, top to bottom:
1. **Connected repo** card — repository URL (truncated, full value on
   hover), branch, access-token state badge ("Set" / "Not set (public
   repo)"), an "Edit" button that swaps back to the connect-style form
   pre-filled with the current URL/branch (token field starts blank).
2. **Webhook** card — any server warnings (e.g. no dashboard domain
   configured, so the URL is relative) shown first; the payload URL in a
   monospace box with a copy button; the secret in the same style with
   copy + a "Rotate" button behind a small popover confirm (warns that
   any webhook already configured on the forge needs updating); below
   that, a 3-item accordion (GitHub / GitLab / Gitea, opened to the
   detected provider) with each forge's concrete webhook-setup steps.
3. **Manual deploy** card — one sentence naming the configured branch,
   "Deploy now" button. On success, `AppDetail` switches to the
   Deployments tab and auto-expands that deployment's build-log drawer
   (`BuildLogPanel`), so the SSE build log streams exactly like a tarball
   deploy's does — no separate log viewer was built for this tab.
4. **Recent deliveries** card — a table (When / Branch / Commit /
   Outcome / deployment #), manual Refresh button (no polling). Outcome
   is a colored badge (`Deployed` emerald, `Ignored — wrong branch` /
   `Ignored — not a push` slate, `Rejected — bad signature` red, `Rate
   limited` / `Queued` amber) **plus** the server's own human-readable
   `detail` string underneath — e.g. `push to "refs/heads/dev", configured
   branch is "main"` — so a silent-push debugging session reads the
   actual reason, not a status enum.
5. **Danger zone** card — red-ringed, "Disconnect" behind
   `ConfirmDanger` (type the app slug to confirm), explaining the
   webhook stops and secret/token are deleted while the app and its
   deployment history are untouched.

**Narrow width:** all cards are single-column already (no grid); the
webhook URL/secret rows wrap their copy/rotate buttons onto a second line
via flex-wrap rather than overflowing; the deliveries table scrolls
horizontally inside its own container if needed (Nuxt UI's `UTable`
default).

### Compose source (NewApp.vue → "Compose")

Radio source picker (Image / Upload / Compose) at the top, same as
before. Selecting Compose replaces the Name/Image/Port fields entirely
(a compose upload creates N apps, not one) with:

**Step 1 (idle):** Project name (optional — hint explains it falls back
to the file's own `name:` if left blank), a `.tar.gz` file picker (hint
points at `basepod compose up` for local-folder packaging), "Preview
plan" button (disabled until a file is chosen and the project name, if
any, is a valid slug shape).

**Step 2 (preview, after a successful dry run):** `ComposePreview`
renders — project name + service count + a "Dry run" badge; a prominent
amber warning callout listing every top-level + per-service warning
(count in the title) if any exist; an amber "Orphaned services from a
prior apply" callout naming exactly which slugs are still running and
unaffected, if this project has any (never implies they were cleaned
up); then a responsive 2-column (1-column narrow) grid of per-service
cards — service name + slug, a Create/Update badge, an internal/port
badge, a `replace strategy` badge when applicable (with the *why*
appended to that service's own warnings list, since the Go plan response
puts the reason there), and any of that service's own warnings listed
below. A "Confirm & apply" button at the bottom (only shown for a dry
run) re-posts the same upload with `dry_run=0`.

**Step 3 (applied):** the same `ComposePreview`, now showing "Applied"
instead of "Dry run" and each service's real `deployment_number` as a
green badge; a "Done" button returns to the Apps list.

Errors at any step render as an inline `UAlert`; an apply-time failure
(rare, since the dry run already validated the plan) drops back to the
preview step rather than discarding the uploaded file, so retrying
"Confirm & apply" doesn't require re-selecting the file.

**Narrow width:** the compose form widens its container slightly
(`max-w-3xl` vs `max-w-2xl` for image/upload) since the service-card grid
needs more room; the grid itself collapses to one column below `sm`.

### Apps list grouping (Apps.vue)

With no compose apps present, the list is **pixel-identical to before**
— no headers, no chrome (verified by making `showGroupHeaders` false
whenever the only group is the standalone bucket). Once at least one
compose app exists:
- Standalone (non-compose) apps render first under a muted "STANDALONE"
  label with a box icon and count.
- Each compose project gets its own section: a "boxes" icon, the project
  name in uppercase tracking, its service count, and a "Delete project"
  ghost button (red) on the right.
- Within a project's rows, the displayed name is the **service** name
  (e.g. `web`, `db`), not the full `<project>-<service>` slug — the slug
  is still what the row links to and what powers `RouterLink`.
- An internal service (no `expose:` in the compose file) shows a small
  lock-icon "Internal" badge next to its status badge, and its Port
  column reads "—" / "internal" instead of a port number (internal
  services carry `port: 0` server-side, which would otherwise render as
  a misleading literal `0`).
- "Delete project" opens `ConfirmDanger` with the project name as the
  type-to-confirm text and a description that names every app slug about
  to be deleted; on confirm it fires one `DELETE` per app
  (`Promise.allSettled`, so a partial failure doesn't abandon the ones
  that succeeded) and refetches the list either way.

**Narrow width:** unchanged from the existing responsive behavior — the
same `md:` breakpoint swap between the grid table and stacked cards,
now repeated per group; group headers stay full-width single lines at
any width.
