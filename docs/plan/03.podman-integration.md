# 03 — Podman Integration

## Principles

1. **Rootless first.** Everything works as an unprivileged user; root is
   an optimization, never a requirement.
2. **The socket is the contract.** All container operations go through the
   Podman REST API socket via the official Go bindings
   (`github.com/containers/podman/v5/pkg/bindings`). No shelling out to
   `podman` except where the API has no equivalent (documented per case).
3. **Supervision belongs to the OS where possible.** Linux: systemd via
   Quadlet. macOS: BasePod supervises (no systemd inside reach).
4. **Everything we create is labeled.** We only ever touch resources
   carrying our labels.

## Socket discovery

Order: `podman.socket` config value → `$XDG_RUNTIME_DIR/podman/podman.sock`
(Linux rootless) → `/run/podman/podman.sock` (root) → `podman machine
inspect` connection URI (macOS, ssh:// forwarded socket). Health-checked
at startup and continuously (doc 02 covers the macOS VM-down state).

## Runtime abstraction

A single interface so the rest of the codebase never imports Podman types:

```go
type Runtime interface {
    PullImage(ctx, ref string, auth *RegistryAuth) error
    BuildImage(ctx, opts BuildOptions) (imageID string, err error)
    CreateContainer(ctx, spec ContainerSpec) (id string, err error)
    StartContainer / StopContainer / RemoveContainer(ctx, id) error
    ListManaged(ctx) ([]ContainerInfo, error)        // filtered by label
    ContainerLogs(ctx, id, opts LogOptions) (io.ReadCloser, error)
    ContainerStats(ctx, id) (Stats, error)
    EnsureNetwork / EnsureVolume(ctx, name string) error
    Exec(ctx, id string, cmd []string, tty bool) (Conn, error)
}
```

Implementations: `podmanRuntime` (bindings). A `fakeRuntime` backs unit
tests (doc 11).

## Naming & labels

| Resource | Convention |
|---|---|
| Container | `bp-<app>-<deploymentID>` (e.g. `bp-blog-42`) |
| Network | `basepod` (one shared bridge; per-team networks in phase 4+) |
| Volume | `bp-<app>-<volumeName>` |
| Image tag | `localhost/basepod/<app>:<deploymentID>` |

Labels on every resource: `basepod.managed=true`, `basepod.app=<name>`,
`basepod.deployment=<id>`, `basepod.team=<slug>`.

**Reconciliation:** on startup and periodically, list resources by label
and diff against SQLite; adopt, restart, or report drift (a container
killed by OOM, a unit disabled by hand). The DB is desired state; Podman
is observed state.

## Linux: Quadlet supervision

For each app deployment BasePod renders a Quadlet `.container` unit into
`~/.config/containers/systemd/bp-<app>.container`:

```ini
[Unit]
Description=BasePod app: blog

[Container]
Image=localhost/basepod/blog:42
ContainerName=bp-blog-42
Network=basepod.network
EnvironmentFile=%h/.local/share/basepod/apps/blog/env
Volume=bp-blog-data:/data:Z
Label=basepod.managed=true "basepod.app=blog" "basepod.deployment=42"
HealthCmd=/bin/sh -c 'wget -qO- http://127.0.0.1:8080/ || exit 1'
HealthInterval=10s

[Service]
Restart=always

[Install]
WantedBy=default.target
```

Then `systemctl --user daemon-reload` + `systemctl --user start
bp-blog.service`. Containers survive reboots (with lingering enabled,
doc 02) and BasePod restarts. Env files are written 0600; secrets never
appear in unit files or `podman inspect` args.

A matching `basepod.network` Quadlet unit defines the shared network.

**Why Quadlet over BasePod-managed restarts on Linux:** systemd gives us
boot-time start, restart backoff, resource cgroups, and journald logging
for free, and it keeps apps alive even if the BasePod daemon itself is
down — the control plane is not a runtime dependency of the apps.

## macOS: direct supervision

No systemd, so:

- Containers created via bindings with restart policy `always` inside the
  `podman machine` VM.
- BasePod runs a supervisor loop: watch Podman events stream; on
  unexpected exit beyond Podman's own restart handling, recreate; on VM
  restart, reconcile all managed containers back to desired state.
- This is explicitly the dev/homelab path; the docs set that expectation.

The `Runtime` interface plus a `Supervisor` interface keeps this split
clean: `systemdSupervisor` (Linux) vs `directSupervisor` (macOS).

## Networking between apps

All app containers join the `basepod` bridge network. Podman's DNS
(aardvark-dns) resolves container names, so apps reach each other at
`bp-<app>` — surfaced in the UI as "internal hostname". App ports are
**not** published to the host; only Caddy (doc 04) reaches them over this
network. Databases provisioned from templates (doc 09) are therefore
internal-only by default.

## Health checks

- Default: TCP connect to the app's declared port.
- Optional HTTP path + expected status in `basepod.yaml` (doc 06).
- Health state feeds zero-downtime deploys (doc 06) and the dashboard.

## Logs & stats

- Logs: bindings `ContainerLogs` (follow mode) → SSE to UI/CLI. On Linux,
  journald is the persistent store (Quadlet default); BasePod streams
  live and reads back recent history (`journalctl --user -u
  bp-<app>`-equivalent via API where possible).
- Stats: bindings stats stream → in-memory ring buffer → dashboard
  sparklines. Long-term metrics are a plugin concern (doc 09), not core.

## Image lifecycle

- Keep the images of the last N (default 5) deployments per app for
  rollback (doc 06); prune older ones nightly, plus `basepod prune`.
- Registry auth stored encrypted (doc 05) for private image pulls.
