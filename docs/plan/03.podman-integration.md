# 03 — Podman Integration

> **Status (v0.3):** DELIVERED — a hand-rolled libpod REST client over a
> Unix socket (`internal/podman/client.go`, not
> `github.com/containers/podman/v5/pkg/bindings`), the real `Runtime`
> interface consumed by the deploy engine
> (`internal/deploy/runtime.go`), label-based naming and boot-time
> reconciliation (network DNS self-heal in `EnsureNetwork`/
> `selfHealNetworkDNS`, Caddy container drift-repair in
> `internal/caddy/manager.go`'s `Ensure`, orphan container GC in
> `internal/deploy/deploy.go`'s `CleanupOrphans` — all run once at boot,
> see `internal/server/server.go`'s `Run`), and an HTTP health probe run
> from inside the `bp-caddy` container (`deploy.CaddyProber`).
> **DESIGN-ONLY** (not built): Quadlet unit generation — supervision is
> Podman's own `--restart=always` policy plus, on a real VPS, a
> hand-enabled `podman-restart.service` systemd unit (see doc 02) — no
> event-stream-watching supervisor loop on any platform, declared
> per-app volumes, configurable/manifest-driven health checks (the real
> probe is a fixed `wget --spider http://<upstream>/`, not TCP-only and
> not path-configurable), image retention beyond the deploy engine's
> built-tag pruning (`pruneBuiltImages`, tarball-built images only —
> pulled/registry images are never pruned), and encrypted registry auth
> for private image pulls (`PullImage` takes no credentials at all — see
> doc 06). The sections below are corrected to describe the real
> `Runtime` interface and the real (boot-time-only, not continuous)
> reconciliation story.

## Principles

1. **Rootless first.** Everything works as an unprivileged user; root is
   an optimization, never a requirement.
2. **The socket is the contract.** All container operations go through the
   Podman libpod REST API socket — but via a small hand-rolled client
   (`internal/podman/client.go`) speaking versioned `/v5.0.0/libpod/...`
   HTTP directly, **not** the official
   `github.com/containers/podman/v5/pkg/bindings` package. Shelling out to
   `podman` is used for two things only: `podman exec` (Caddy admin-API
   reload — no stream-hijacking client), and socket auto-detection
   (`podman system connection list`, `podman machine inspect`).
3. **Supervision belongs to Podman today, not systemd.** The original
   design split this Linux (Quadlet/systemd) vs. macOS
   (BasePod-supervised) — as shipped, **neither exists**: every platform
   relies on Podman's own `--restart=always` container policy, with no
   generated Quadlet units and no BasePod-side event-watching supervisor
   loop. See "Linux and macOS: restart-policy supervision" below.
4. **Everything we create is labeled.** We only ever touch resources
   carrying our labels.

## Socket discovery

Real order, as implemented in `internal/podman.DetectSocket` (used when
`podman_socket` in config.yaml is empty): (1) the *default* entry from
`podman system connection list --format json`, if its URI already uses
`unix://`; (2) `$XDG_RUNTIME_DIR/podman/podman.sock` (Linux rootless);
(3) `/run/podman/podman.sock` (root); (4) `podman machine inspect`'s
forwarded local socket path (macOS). A default connection that resolves
to a non-unix scheme (e.g. `ssh://`, the common shape for `podman
machine`) with no fallback path found returns an actionable error rather
than failing silently. This is checked once at `basepod server` boot
(`Ping` + `Version`), **not continuously** — there is no background
health-check loop; a Podman outage after boot surfaces as individual
API-call failures, not a tracked "VM starting…" UI state (that macOS UX
described in doc 02's original design was never built).

## Runtime abstraction

The real interface the deploy engine and Caddy manager consume
(`internal/deploy/runtime.go`; `caddy.Runtime` in
`internal/caddy/manager.go` is a narrower subset of the same client),
satisfied by `*podman.Client`:

```go
type Runtime interface {
    PullImage(ctx, ref string) error
    ImageExists(ctx, ref string) (bool, error)
    RemoveImage(ctx, ref string, force bool) error
    ListImageTags(ctx, repoPrefix string) ([]string, error)
    CreateContainer(ctx, spec podman.CreateSpec) (string, error)
    StartContainer(ctx, id string) error
    StopContainer(ctx, id string, timeoutSec int) error
    RemoveContainer(ctx, id string, force bool) error
    InspectContainer(ctx, nameOrID string) (*podman.ContainerInfo, error)
    ListContainers(ctx, labelFilters map[string]string) ([]podman.ContainerInfo, error)
    ContainerLogs(ctx, nameOrID string, follow bool, tail int) (io.ReadCloser, error)
}
```

There is no `BuildImage(opts BuildOptions)` on this interface — building
is a separate, lower-level `*podman.Client.BuildImage(tag, dockerfile,
contextTar, logSink)` method called directly by `internal/build.Builder`
(doc 06), not through the `Runtime` seam above. `ContainerStats` and
`Exec(id, cmd, tty)` don't exist at all — no stats streaming, no
interactive exec (see doc 05's endpoint map). `ListManaged` is really
`ListContainers(labelFilters)` — callers pass the label filter
explicitly rather than a fixed "managed" query.

Implementation: `*podman.Client` (the real libpod REST client). Fakes
implementing this same interface back the unit test suites in
`internal/deploy` and `internal/caddy` (doc 11).

## Naming & labels, and instance identity

| Resource | Convention | Status |
|---|---|---|
| Container | `bp-<app>-<deploymentNumber>` (e.g. `bp-blog-42`) | delivered — `internal/deploy.runRollout` |
| Network | `basepod` (one shared bridge) | delivered — `caddy.NetworkName`; per-team networks (phase 4+) is design-only, there being no teams |
| Network alias | `bp-<app>` (Caddy and other apps resolve the app by this DNS name) | delivered |
| Volume | `bp-<app>-<volumeName>` | **design-only** — no app ever gets a volume mount; `podman.CreateSpec.Mounts` is only used by `caddy.Manager` for its own config/data/socket bind mounts |
| Image tag | `localhost/basepod/<app>:<deploymentNumber>` | delivered, tarball-built deploys only — `internal/deploy.builtImageRepo` |

Labels actually set on every app/Caddy container: `basepod.managed=true`,
`basepod.app=<slug>`, `basepod.deployment=<deploymentNumber>` (app
containers only — `bp-caddy` carries just `basepod.managed=true` plus
`basepod.instance`, below), and — as of the issue #10 fix —
`basepod.instance=<id>` on every one of them, plus (where the libpod API
supports network-create labels) the shared `basepod` network itself.
`basepod.team=<slug>` does **not** exist — there is no `teams` table
(doc 05).

**Instance identity (issue #10 fix, `internal/instanceid`):** every
running `basepod server` process has a stable id, a random string
persisted at `<data_dir>/instance.id` (a sibling of `secret.key`) on first
boot and never regenerated — `instanceid.LoadOrCreate` mirrors
`crypto.LoadOrCreateKey`'s atomic-create-or-read shape exactly (write a
temp file, rename it into place, re-read what's actually on disk, guarded
by a `sync.Mutex` for a same-process concurrent first-boot race). This
exists because `basepod.managed=true` alone is identical across every
BasePod install: on a host running two instances against two data dirs
(a dev box next to production, two test instances, or — the incident that
filed issue #10 — a throwaway instance started against an empty temp data
dir next to a live one) "is this container mine?" can't be answered by
that label alone. `basepod.instance=<id>` can.

**Reconciliation, as actually implemented:** runs **once, at
`basepod server` boot** (`internal/server.Run`), not continuously or on
a periodic timer. Three separate mechanisms, not one generic
list-and-diff loop — all three now instance-scoped:
- `podman.Client.EnsureNetwork` self-heals a `basepod` network that
  exists but has DNS resolution disabled (only when no basepod-managed
  container is currently attached — otherwise it just logs a warning
  with manual remediation steps, since recreating a network under a
  live container would break its networking). It also stamps
  `basepod.instance=<id>` on the network at create time, for
  forensic/audit visibility only — the network is a single shared
  resource by design (the name `basepod` is a fixed constant), so unlike
  the two mechanisms below, an existing network is never refused or
  recreated over an instance-id mismatch.
- `caddy.Manager.Ensure` detects `bp-caddy` drift (wrong image, wrong
  port mapping, wrong bind-mount set, or stuck in `created`) and
  recreates the container if so — but only once it has confirmed
  ownership: a `bp-caddy` labeled with a **different** instance's id
  is never touched (no drift check, no start, no recreate) — `Ensure`
  returns a clear, boot-failing error explaining that two BasePod
  instances appear to share this Podman socket instead. A `bp-caddy`
  with **no** `basepod.instance` label at all (the shape every
  pre-v0.5 install's container has) is adopted exactly as before
  instance ids existed, and only picks up this instance's own label
  the next time a real drift condition (e.g. an image bump) forces an
  actual recreate.
- `deploy.Engine.CleanupOrphans` removes any container it owns whose app
  no longer exists in the store, or whose deployment generation isn't
  the app's latest *healthy* one — "owns" now means: labeled with this
  instance's id, OR unlabeled with a slug this instance's own database
  already knows about (the upgrade-adoption case — see below). A
  container labeled with a **different** instance's id is skipped
  outright, its slug never even looked up: matching by slug alone
  across instances is exactly the bug issue #10 reports, since a slug
  collision between two independent instances' apps is entirely
  possible. An **unlabeled** container whose slug this instance's
  database does *not* recognize is left strictly alone and logged
  loudly ("possibly another instance's, not touching") — GC never
  deletes an unlabeled container on a guess, which is what actually
  destroyed a live instance's container in the incident this fix
  closes. `removeOldContainers`, `fail`, `RemoveApp`, `AppLogs`, and
  `AppStats` apply the same "skip a differently-instance-labeled
  container" filter defensively, in case two instances' apps ever share
  a slug by coincidence.

None of these "adopt" an out-of-band container into the DB's desired
state in the general case — they only clean up, recreate, or (for the
specific unlabeled-plus-known-slug case above) adopt. None restart a
container that Podman itself didn't already restart via its own policy.
A container that dies mid-run and Podman's `--restart=always` doesn't
bring back stays down until the next `basepod server` boot or a fresh
deploy.

## Linux: Quadlet supervision — **design-only, not built**

**As delivered in v0.3:** no Quadlet units are rendered at all, on
Linux or anywhere else. Every container (app or `bp-caddy`) is created
via `podman.CreateSpec{RestartPolicy: "always"}` and left to Podman's
own restart-policy engine. For that to survive a host **reboot** (not
just a crash while the host stays up), the operator must separately
enable Podman's own `podman-restart.service` for their user session
(`systemctl --user enable --now podman-restart.service` — see doc 02);
BasePod does not enable this for you. Env vars are passed as plain
container `Env` in the create request (still 0600-readable only via
`podman inspect` by whoever can already reach the socket — there is no
separate env-file-on-disk step to keep 0600 either way).

The rest of this section describes the **original Quadlet design**,
kept as the intended future direction (doc 03's "why Quadlet" rationale
below still holds) — none of it is implemented today.

For each app deployment BasePod renders a Quadlet `.container` unit into
`~/.config/containers/systemd/bp-<app>.container`:

```ini
[Unit]
Description=BasePod app: blog

[Container]
Image=localhost/basepod/blog:42
ContainerName=bp-blog-42
Network=basepod.network
EnvironmentFile=%h/.local/share/basepod/apps/blog/env
Volume=bp-blog-data:/data:Z
Label=basepod.managed=true "basepod.app=blog" "basepod.deployment=42"
HealthCmd=/bin/sh -c 'wget -qO- http://127.0.0.1:8080/ || exit 1'
HealthInterval=10s

[Service]
Restart=always

[Install]
WantedBy=default.target
```

Then `systemctl --user daemon-reload` + `systemctl --user start
bp-blog.service`. Containers survive reboots (with lingering enabled,
doc 02) and BasePod restarts. Env files are written 0600; secrets never
appear in unit files or `podman inspect` args.

A matching `basepod.network` Quadlet unit defines the shared network.

**Why Quadlet over BasePod-managed restarts on Linux:** systemd gives us
boot-time start, restart backoff, resource cgroups, and journald logging
for free, and it keeps apps alive even if the BasePod daemon itself is
down — the control plane is not a runtime dependency of the apps.

## macOS: direct supervision

**As delivered:** the same as Linux — `RestartPolicy: "always"` on
container create, nothing more. There is no BasePod-side supervisor
loop watching the Podman events stream anywhere in the codebase, on
either platform: no unexpected-exit recreation beyond what Podman's own
restart policy already does, and no VM-restart reconciliation beyond
what `CleanupOrphans` + the Caddy drift-check already do once at the
next `basepod server` boot. The `Supervisor`
(`systemdSupervisor`/`directSupervisor`) split described below was
never built — there is exactly one supervision path (Podman's restart
policy) shared by every platform, not two.

This remains explicitly the dev/homelab path on macOS; the docs set
that expectation.

**Note on Caddy and the VM boundary:** Caddy runs as a container on the
`basepod` network inside the VM, so it reaches app upstreams by DNS name
on that network — no published-port fallback or host-IP routing needed.
This is the same on macOS and Linux.

## Networking between apps

All app containers join the `basepod` bridge network, which is created
with DNS enabled (aardvark-dns) — a hard requirement. Podman's DNS
resolves container names, so apps reach each other at `bp-<app>` — surfaced
in the UI as "internal hostname". This same DNS enables Caddy (doc 04) to
reach app upstreams by name on all platforms (Linux and macOS) without
exposed host ports or VM boundary routing complexity. App ports are
**not** published to the host; only Caddy reaches them over this network.
Databases provisioned from templates (doc 09) are therefore internal-only
by default.

## Health checks

**As delivered** (`deploy.CaddyProber` in `internal/deploy/deploy.go`):
a single fixed HTTP probe — `wget -q -T 2 --spider http://<upstream>/`
run via `podman exec` **inside the `bp-caddy` container** (which shares
the `basepod` network and ships busybox `wget`), retried once a second
for up to 30 attempts (`Engine.probeInterval`/`probeAttempts`). An HTTP
error response (wget exit 8) still counts as "up" — the upstream
answered, even if `/` 404s. This is **not** a TCP-only check as
originally designed, is **not** configurable (no path, no expected
status, no per-app override), and there is no `basepod.yaml` manifest
to configure it from (doc 06). Health state does feed the zero-downtime
cutover (doc 06) — a probe that never succeeds means the new container
is torn down and the deployment marked `failed` without disturbing the
old one — but there is no dashboard-visible ongoing health indicator
beyond an app's current `status` column.

## Logs & stats

- **Logs — delivered:** `podman.Client.ContainerLogs` (follow mode
  supported) streams the running container's raw, still-multiplexed log
  data; `internal/api`'s `/apps/{slug}/logs` handler demuxes it into
  SSE for the UI/CLI (doc 05). There is no journald integration in code
  — under systemd, a unit's stdout naturally lands in the journal, but
  BasePod doesn't read it back through any `journalctl`-equivalent API;
  history comes from Podman's own log buffer via the `tail` parameter,
  same on every platform.
- **Stats — design-only.** No stats streaming exists: no
  `ContainerStats` method on the `Runtime` interface, no in-memory ring
  buffer, no dashboard sparklines, no `/apps/{slug}/stats` endpoint
  (doc 05).

## Image lifecycle

- **Delivered, but narrower than designed:** `Engine.pruneBuiltImages`
  keeps the newest `retainBuiltImages` (5) numbered
  `localhost/basepod/<slug>:<n>` tags after every successful rollout,
  always protecting the currently-running image even if it falls
  outside that top-5 window (e.g. after a rollback to an older tag).
  This only prunes **tarball-built** local tags — pulled/registry images
  are never pruned, there is no nightly sweep, and no `basepod prune`
  CLI command exists.
- **Design-only:** encrypted registry auth for private image pulls.
  `PullImage(ctx, ref)` takes no credentials parameter at all — only
  public refs (or refs the local Podman already has cached auth for)
  can be pulled. There is no `registries` table (doc 05).
