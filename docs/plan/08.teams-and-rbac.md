# 08 — Teams, Users & RBAC

> **Status: not implemented.** Through v0.3, BasePod ships single-admin
> auth only: the one admin account created by `basepod setup`, sessions
> (argon2id password hashing, session tokens, server-side logout, and
> expired-session pruning — see `internal/auth` and the `users`/
> `sessions` tables in `internal/store/migrations/00001_init.sql`). There
> are no additional users, no teams, no roles, no API tokens, and no
> audit log — everything below this line is the design for a later
> milestone (currently slotted after v0.4 in doc 11's roadmap), not
> current behavior. The concrete v0.3 auth surface this design must
> eventually extend — rather than replace — is `internal/auth`'s
> password/session handling and the `users`/`sessions` schema; expect
> that schema to grow team/role/token columns and tables rather than be
> rebuilt from scratch.

## Model

- **User** — a person (email + password, later TOTP). A special
  `is_superadmin` flag marks instance operators.
- **Team** — the ownership boundary. Every app belongs to exactly one
  team. Every user belongs to ≥ 1 team. Setup creates a `default` team
  with the first admin as owner, so solo users never think about teams
  unless they want to.
- **Membership role** — per (team, user): `owner`, `admin`, `member`,
  `viewer`.

Resources under a team: apps (and their deployments/domains/env/volumes),
registries, team-scoped audit log. Instance-level resources (settings,
plugins, servers, users directory): superadmin only.

## Permission matrix (enforced server-side, mirrored in UI)

| Capability | viewer | member | admin | owner |
|---|---|---|---|---|
| View apps, logs, deployments, stats | ✓ | ✓ | ✓ | ✓ |
| Deploy, restart, rollback | | ✓ | ✓ | ✓ |
| Create/delete apps | | ✓ | ✓ | ✓ |
| View env values (secrets stay write-only for all) | | ✓ | ✓ | ✓ |
| Edit env, domains, volumes, app settings | | ✓ | ✓ | ✓ |
| Exec into containers (terminal) | | | ✓ | ✓ |
| Manage registries | | | ✓ | ✓ |
| Manage members & roles (≤ own role) | | | ✓ | ✓ |
| Rename team, transfer/remove owner, delete team | | | | ✓ |
| Team audit log | | | ✓ | ✓ |

Enforcement: a single `authorize(user, team, capability)` function in
`internal/auth`, called by API middleware from a route→capability table.
No permission checks scattered in handlers. Table-driven tests cover the
full matrix (doc 11).

## Invitations

v1: an admin creates an invite → tokenized link (7-day expiry, single
use) → invitee sets name/password and lands in the team with the chosen
role. Email delivery is out of scope for core (no SMTP dependency);
the link is displayed for the admin to share. An SMTP/notifications
plugin (doc 09) can automate sending later.

## API tokens & automation

- PATs belong to a user and can be **scoped down**: `read` / `deploy` /
  `admin`, optionally restricted to one team or one app. Effective
  permission = intersection(user's role, token scope) — a token never
  out-ranks its owner, and revoking membership kills token access too.
- Deploy tokens for CI: the common case is a PAT with scope
  `deploy` + app restriction; the UI has a shortcut ("create CI token
  for this app") emitting copy-paste CI snippets (GitHub Actions
  example in docs).

## Audit log

Every mutating API call writes one row (doc 05 schema): actor (user or
token), team, action (`app.deploy`, `env.update`, `member.role_change`,
…), resource, detail JSON (diff-style where cheap — e.g. env keys
changed, not values), IP. Secrets never logged. Retention: 90 days
default, configurable; superadmin can export CSV.

## Security posture (v1 commitments)

- Rate-limited login + PAT auth; constant-time comparisons.
- Session revocation UI ("log out other sessions").
- All RBAC decisions server-side; the SPA only *hides* what the API
  already *denies*.
- Superadmin actions on other teams are themselves audit-logged.
- TOTP 2FA: post-v1, schema-ready (doc 05).
