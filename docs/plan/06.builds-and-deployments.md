## Deploy sources

| Source | How it arrives | Build step? |
|---|---|---|
| **Image** | UI/API/CLI provides `ghcr.io/user/app:tag` | No — pull only |
| **CLI tarball** | `basepod deploy` tars cwd → `POST /deploy/tarball` | Yes |
| **Git** | Webhook (push event) or manual "deploy branch" button | Yes — server clones |
| **Compose** | `compose.yaml` via UI/CLI | Per-service (build or pull) |

## App manifest — `basepod.yaml` (optional, in repo root)

```yaml
# all fields optional; flags/UI override
name: blog
port: 8080                 # container port to expose
healthcheck:
  path: /healthz           # default: TCP connect on port
build:
  containerfile: ./Containerfile   # default: auto-detect
  context: .
  args: {NODE_ENV: production}
env:                       # non-secret defaults; secrets set via UI/CLI
  TZ: Europe/Tirane
volumes:
  - data:/var/lib/app
resources:
  memory: 512m
  cpus: 1.0
```

Equivalent of CapRover's `captain-definition`, but YAML and optional:
zero-config deploys must work.

## Build pipeline

States: `queued → building → deploying → healthy | failed`.

1. **Acquire source** — untar upload / `git clone --depth 1 -b <branch>`
   (deploy keys or https+token from encrypted registry/creds store).
2. **Resolve build strategy**:
   - `Containerfile`/`Dockerfile` present (or set in manifest) → podman
     build via bindings, build args from manifest.
   - No Containerfile → **v1**: fail with a helpful message + template
     suggestions ("detected Node.js — here's a starter Containerfile").
     **v1.x**: buildpack auto-detection (nixpacks-style) as a builtin
     plugin (doc 09) — keeps core small.
3. **Tag** `localhost/basepod/<app>:<deploymentN>`.
4. **Deploy** (below). Build log captured to
   `<data_dir>/apps/<app>/builds/<n>.log`, streamed live via SSE.

Build concurrency: one build per app at a time (later deploy of same app
supersedes queued ones); global cap (default 2) to protect small VPSes.
Timeout default 15 min.

## Zero-downtime deploy (default strategy)

1. Create new container `bp-<app>-<n>` (new Quadlet unit on Linux)
   alongside the old one — same network, same volumes.
2. Wait for health (doc 03) with deadline (default 60 s).
3. Healthy → Caddy manager swaps the route upstream to the new
   container's address (atomic full-config load, doc 04). Old container
   gets 30 s drain, then stopped and removed (unit removed too).
4. Unhealthy → new container destroyed, deployment marked `failed`, old
   keeps serving. **A failed deploy never takes the app down.**

Caveats documented: apps holding exclusive volume locks (e.g. SQLite
apps) can opt into `strategy: replace` (stop-then-start, brief downtime)
in the manifest. `instances > 1` (same-host replicas behind Caddy
load-balancing) is supported for stateless apps; replicas roll one at a
time.

## Rollback

`basepod rollback <app> [n]` / UI button: re-deploy a retained image
(last 5 kept, doc 03) through the same zero-downtime path, with the
deployment's env snapshot (env changes create a deployment too, so
rollback restores config + code together).

## Git integration (phase 5)

- Per-app webhook URL `POST /webhooks/git/<app-uuid>/<secret>` with
  HMAC verification (GitHub `X-Hub-Signature-256`, GitLab token, Gitea) —
  branch filter from app config.
- v1 is provider-agnostic generic webhooks (works with any host).
  Deeper GitHub App integration (commit statuses, PR preview apps) is a
  plugin candidate (doc 09).

## Compose support (phase 5)

- Accept a `compose.yaml`; translate the supported subset (services,
  image/build, env, volumes, depends_on, expose) into one BasePod app
  per service, linked by the shared network, DNS names preserved via
  network aliases matching service names.
- Unsupported keys → explicit warnings, never silent drops.
- Implementation candidates: `podman kube play` via generated K8s YAML,
  or direct translation to our own model. **Decision: direct
  translation** — keeps everything (domains, env UI, rollbacks) working
  per-service; kube play would bypass our model.

## CLI

Same binary, client mode; config at `~/.config/basepod/cli.yaml`
(contexts: multiple servers, current context, PAT).

```
basepod login https://basepod.example.com      # opens browser or prompts for PAT
basepod context list|use <name>

basepod apps [ls|create|delete|info <app>]
basepod deploy [-a <app>] [--image ref] [path]  # default: tar cwd, respect .basepodignore
basepod logs <app> [-f] [--tail 200]
basepod env <app> [set K=V ... | unset K | pull | push .env]
basepod domains <app> [add|rm <hostname>]
basepod rollback <app> [n]
basepod exec <app> [--] <cmd>       # interactive over WebSocket
basepod ps / status                 # server overview
basepod server / setup / upgrade / backup / uninstall   # host-side commands
```

UX details: `deploy` streams build + deploy progress with clear phases
and exits non-zero on failure (CI-friendly); `--json` on read commands
for scripting; helpful error when the daemon is unreachable.
