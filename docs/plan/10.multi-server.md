# 10 — Multi-Server (Phase 7)

> **Status: not implemented.** BasePod is single-server only through
> v0.3 — there is no `basepod agent` mode, no `/servers` API, and no
> `server_id` column anywhere in the schema (checked against all three
> migrations in `internal/store/migrations/`: `00001_init.sql`,
> `00002_env_domains.sql`, `00003_deploy_sources.sql`). The "designed in
> from day one" claim below does not hold in the current schema — adding
> `server_id` (and the rest of this phase) will require an actual
> migration against existing tables (`apps`, `deployments`, and whatever
> this phase adds), not just new capability on top of already-generic
> columns. Treat this document as a design doc only.

Built last, designed first *(aspirational — see status note above)*: the
schema (`server_id` everywhere), API (`/servers`), and internal
interfaces were meant to assume multiple servers from day one so this
phase would add capability, not migrations of everything; that groundwork
was not actually laid in v0.1–v0.3.

## Model

**Controller + agents.** The existing `basepod server` is the
controller. Additional machines run `basepod agent`, which is the same
binary running only: Podman manager, local Caddy (optional, see routing),
log/stat streaming, and an outbound connection to the controller.

- **Agent connects outward** (WebSocket over HTTPS to the controller) —
  works behind NAT/firewalls, no inbound ports on workers, no SSH
  key management. Controller never dials agents.
- Join flow: controller UI → "Add server" → one-shot join token →
  `basepod agent join https://controller --token …` on the worker →
  agent stores its long-lived credential, appears in the Servers screen.
- Heartbeats + capability report (arch, resources, podman version).
  `servers.status`: `online | unreachable | draining | disabled`.

## Placement

v1 of multi-server is deliberately simple:

- Each app is **pinned to one server** (chosen at creation, movable).
- "Move app" = deploy to target server (image push or rebuild there) →
  health check → flip routing → remove from source. Volumes move via
  tar-stream through the controller (with size warnings); documented as
  a maintenance operation.
- No scheduler, no spreading, no affinity rules in the first cut.
  `instances: N` stays same-server. Cross-server replicas and automatic
  placement are explicitly future work.

## Routing options

Default (simple, v1): **each server runs its own Caddy** and serves its
own apps' domains directly — DNS for an app's domain points at the
server hosting it. The controller manages every server's Caddy config
remotely through the agent. Wildcard DNS setups get per-app DNS records
generated instructions in the UI.

Optional later: controller-as-edge (controller's Caddy proxies to apps
on workers over an internal network/WireGuard). Deferred — it introduces
a SPOF and bandwidth funnel that contradicts the simple model.

## Builds

Default: build on the target server (agents can build). Optional
"builder role": designate one beefy server to build and push images to
an internal registry. The controller runs a private registry
(`registry:3` as an internal app) when multi-server is enabled, so
image moves don't need rebuilds. Cross-arch (amd64 controller,
arm64 worker): build happens on a same-arch machine — v1 rule is
"builds run on the target server unless a same-arch builder exists";
qemu-based cross-builds documented but not automated.

## Agent protocol sketch

WebSocket, JSON messages, controller-authoritative:

```
controller → agent: ensure_app{spec}, remove_app, fetch_logs{follow},
                    caddy_config{json}, exec{...}, pull/build{...}
agent → controller: heartbeat{stats}, event{podman event}, log_chunk,
                    build_progress, state_report{reconciliation diff}
```

Agent is stateless beyond its credential + local Podman state: on
reconnect the controller replays desired state and the agent reconciles
(same reconciliation engine as doc 03 — it's the local/remote seam that
the `Runtime`/`Supervisor` interfaces were designed for).

## Failure semantics (documented honestly)

- Controller down: apps keep running everywhere (systemd), agents
  buffer events, deploys unavailable. Same story as single-server.
- Agent/server down: its apps are down (no rescheduling in v1);
  UI shows it loudly; `server.unreachable` event fires (hooks → alerts).
- Split brain is avoided by design: agents never act autonomously
  beyond local supervision of already-declared state.

## Team interaction

Servers are instance-level resources (superadmin manages), but teams can
be **granted placement rights** to specific servers — the app-creation
server picker shows only granted servers. Audit log records placement
changes.
