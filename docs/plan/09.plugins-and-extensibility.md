# 09 — Plugins & Extensibility

## Philosophy

Core stays small: run apps, route traffic, manage teams. Everything else
— metrics stacks, notification integrations, buildpacks, backup targets,
PR preview environments — should be *possible without forking BasePod*.

Three extension surfaces, from simplest to most powerful:

## 1. Templates (one-click apps)

A template is a YAML file describing a deployable app (or group):

```yaml
name: postgres
title: PostgreSQL 17
description: Relational database
category: databases
apps:
  - name: "{{ .Name }}"
    image: docker.io/library/postgres:17
    port: 5432
    internal_only: true          # no Caddy route, no public domain
    env:
      POSTGRES_PASSWORD: "{{ randomSecret 24 }}"
      POSTGRES_DB: "{{ .Name }}"
    volumes: [pgdata:/var/lib/postgresql/data]
after_notes: |
  Connect from other apps at bp-{{ .Name }}:5432
```

- Rendering: Go text/template with a small, documented function set
  (`randomSecret`, `randomPassword`, user-prompted variables declared in
  the template).
- Sources: built-in catalog in a `basepod-templates` git repo (seeded
  with ~15 essentials: Postgres, MySQL, Redis, MinIO, Ghost, Uptime
  Kuma, n8n, …); teams can add extra catalog repos (any git URL) in
  Settings. Compose files (doc 06) cover the "bring your own stack"
  case, so templates stay curated and simple.
- Surfaced in the new-app wizard (doc 07).

## 2. Hooks (events out)

Declarative reactions to lifecycle events — no code, just HTTP:

- Events: `app.created`, `app.deleted`, `deployment.started`,
  `deployment.healthy`, `deployment.failed`, `domain.added`,
  `tls.error`, `member.added`, `server.unreachable`, …
- Subscribers: **webhooks** (URL + HMAC secret, JSON payload, retries
  with backoff, delivery log in UI). Configured per team or per app.
- This alone covers Slack/Discord/Telegram notifications via their
  webhook endpoints, and custom glue via any serverless function.
- Internally, the same event bus drives the UI `/events` SSE stream and
  plugin dispatch — one publisher, three consumer kinds.

## 3. Plugins (OCI-image services)

A plugin is a container image plus a manifest — it runs as a managed
internal app with extra privileges granted by the manifest. Natural fit:
a PaaS already knows how to run containers.

`plugin.yaml` (inside the image, label-referenced):

```yaml
name: metrics
version: 1.2.0
description: Prometheus + per-app dashboards
basepod_min_version: 0.5.0
permissions:
  - events:subscribe            # receive event stream
  - api:read                    # scoped service token, read-only API
  - api:apps:deploy             # (each scope reviewed at install time)
  - podman:stats                # host stats endpoint access
ui:
  nav: {title: Metrics, icon: chart-bar, path: /}
  # plugin serves its UI over HTTP; BasePod proxies it at
  # /plugins/metrics/* with auth enforced by the core first
config_schema:                  # JSON Schema → auto-generated settings form
  type: object
  properties:
    retention_days: {type: integer, default: 30}
hooks:
  deployment.healthy: POST /hooks/deploy   # delivered into the container
```

Mechanics:

- Install = pull image → read manifest → show requested permissions for
  explicit approval (superadmin) → run on the `basepod` network with a
  **scoped service token** minted for exactly the approved API scopes.
- Plugins talk to BasePod via the same public REST API — no private
  interfaces to stabilize; the OpenAPI spec is the plugin SDK. Events
  arrive via SSE subscription or delivered hooks (above).
- UI integration v1 is deliberately simple: reverse-proxied plugin pages
  in an iframe with BasePod chrome (nav entry from manifest). No
  frontend module federation until real demand exists.
- Lifecycle: enable/disable/uninstall from the Plugins screen;
  plugin state in its own volume; upgrades = image tag bump with
  manifest re-approval when permissions change.

**Trust model:** v1 plugins are "install what you trust" (like Grafana
plugins) — permission review at install is the guardrail; there is no
sandbox beyond the container boundary and API scopes. Signed
plugins/registry curation is future work.

### Candidate first-party plugins (validate the API by building on it)

1. **nixpacks-builder** — buildpack auto-detection for repos without a
   Containerfile (doc 06 hands off to it).
2. **notifications** — polished Slack/Discord/email routing on top of
   hooks, with templates.
3. **metrics** — Prometheus + preconfigured dashboards per app.
4. **backup-s3** — scheduled volume + DB backups to S3-compatible
   storage.

Two of these (builder, notifications) ship with v1.0 to prove the
plugin surface is real, not aspirational.

## What is *not* a plugin

Auth/RBAC, the deploy pipeline, Caddy management, Podman management —
core invariants stay in core so the security model remains auditable.

## Feature checklist

- [ ] Event bus (internal) + `/events` SSE + webhook subscribers with
      retries and delivery log
- [ ] Template engine + built-in catalog repo + custom catalog sources
- [ ] Plugin manifest parse/validate + permission approval flow
- [ ] Scoped service tokens (reuses PAT machinery, doc 08)
- [ ] Plugin proxy (`/plugins/<name>/*`) with core-enforced auth
- [ ] Config-schema → settings form generation (doc 07)
- [ ] Plugins screen (install by image ref, enable/disable, logs)
- [ ] First-party: nixpacks-builder, notifications
- [ ] Plugin author guide in docs
