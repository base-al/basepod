# 11 — Testing, Release Engineering & Roadmap

## Testing strategy

> **Status (v0.3):** the rows below are split into what actually exists
> today versus what's still planned — this table used to describe the
> aspirational end state as if it were current; it wasn't.

**Exists today:**

| Layer | Tooling | What it covers |
|---|---|---|
| Unit | `go test ./...` across `internal/*` packages, `fakeRuntime` test doubles (`internal/deploy/deploy_test.go`, `internal/build/build_test.go`, `internal/caddy/manager_test.go`), in-memory/temp SQLite | Business logic: deploy orchestration, tarball build pipeline, Caddy config rendering, auth/session handling, config parsing, crypto (secretbox), CLI commands — see the `_test.go` files across `internal/` |
| Golden-file | `internal/caddy/render_test.go` + `internal/caddy/testdata/*.golden.json` (`UPDATE_GOLDEN=1` to regenerate) | Rendered Caddy JSON config for representative app/domain combinations, including the v0.3 dashboard route |
| API integration | `httptest` + real SQLite | Endpoint behavior for apps, deploy (image + tarball), rollback, build-log streaming, logs SSE, env, domains, auth — see `internal/api/*_test.go` |
| Runtime integration | Real Podman against the CI runner's rootless socket (`internal/podman/*_test.go`) | Podman client calls, container lifecycle |
| Frontend unit | Vitest (`web/src/lib/*.test.ts`: `envparse`, `pendingImage`, `relativeTime`, `slugify`) | Pure-logic units in the dashboard's data layer, run in CI's `test` job |
| E2E | [`scripts/e2e-local.sh`](../../scripts/e2e-local.sh), run in CI's `e2e` job | The full real flow against a real `basepod` binary + real rootless Podman + real Caddy: setup → server boot → image-based deploy → HTTPS fetch → redeploy → env vars → custom domains → live log streaming → dashboard shell/assets → dashboard served remotely over HTTPS at `basepod.<root-domain>` → tarball build-from-source deploy + build-log endpoint → rollback → the same flow again driven through the `basepod` CLI (login/apps/deploy/rollback/env/logs) → session logout/token invalidation → app deletion |

**Missing / planned:**

- **`-race`** — `go test` runs without the race detector, in CI and
  locally (`Makefile`'s `test` target and `ci.yml`'s `test` job are both
  plain `go test ./...`). Not yet enabled.
- **macOS CI legs** — there is no macOS runner in CI; both CI jobs run
  on `ubuntu-24.04` only. `podman machine` behavior on macOS (including
  the dashboard-socket limitation documented in the README) is
  exercised by hand, not by CI.
- **arm64 CI** — no arm64 runner job exists; arm64 correctness is
  covered by the release build matrix (cross-compiled, not test-run) and
  by the wrong-arch-image incident fix (see Risks register).
- **Playwright** — no browser-driven frontend test exists; doc 07's
  deferred Playwright smoke flow is substituted by `scripts/e2e-local.sh`'s
  assertions against the real dashboard shell/assets and SSE streams,
  which is real coverage of the served artifacts but not of interactive
  UI behavior.
- **`govulncheck`** — not run anywhere in CI yet; planned for v0.4
  alongside a Go toolchain bump (see roadmap below).
- **OpenAPI conformance** — moot until an OpenAPI spec exists (it
  doesn't yet — see doc 07's frontend-architecture note).
- **RBAC matrix tests** — moot until RBAC exists (doc 08 is unimplemented).

Golden-file tests for generated Caddy config are the one artifact-golden
suite that exists; Quadlet units, launchd plists, and systemd units are
not currently generated by BasePod at all (containers are managed
directly via the Podman API, not via Quadlet), so there is nothing to
golden-test there — doc 03/04 should be checked before assuming Quadlet
is in the current runtime path.

## CI (GitHub Actions)

> **Status (v0.3):** the three-workflow split below (`pr.yml`,
> `integration.yml`, `release.yml`) was the plan and has not been built.
> The single workflow that exists is
> [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml), triggered
> on pushes to `main`/`feat/**`/`fix/**`/`docs/**` and on pull requests,
> with two jobs, both on `ubuntu-24.04`:

- **`test`** — installs Node 22, runs `cd web && npm ci && npm run build
  && npm run type-check && npm test` (Vitest), then installs Go, runs
  `go vet ./...`, `CGO_ENABLED=0 go build ./...`, and `go test ./...
  -count=1`. No `golangci-lint`, `eslint`, or `govulncheck` step exists.
  No arm64 leg.
- **`e2e`** — builds the frontend, installs Go, confirms `podman version`
  (preinstalled on the `ubuntu-24.04` runner image), enables the rootless
  Podman socket (`systemctl --user enable --now podman.socket`), and runs
  [`scripts/e2e-local.sh`](../../scripts/e2e-local.sh) end to end.

Both jobs run on every push and PR — there is no nightly-only or
merge-only tier, since neither job currently needs one (no macOS legs
exist to be slow). The `pr.yml`/`integration.yml`/`release.yml` split,
the lint steps, `govulncheck`, and macOS/arm64 CI legs remain the plan
(see Testing strategy above and the v0.4 roadmap entry below), not
current behavior.

## Release engineering

> **Status (v0.3):** releases so far (`v0.1.0`, `v0.2.0`, `v0.3.0` —
> [github.com/base-al/basepod/releases](https://github.com/base-al/basepod/releases))
> are hand-cut, not produced by the GoReleaser pipeline described below.
> The actual process is: cross-compile `darwin/amd64`, `darwin/arm64`,
> `linux/amd64`, `linux/arm64` tarballs by hand, generate a
> `checksums.txt`, and publish with `gh release create` attaching those
> five assets (e.g. `basepod_v0.3.0_linux_amd64.tar.gz` +
> `checksums.txt`) directly to a tag. No GoReleaser config exists in the
> repo, no Homebrew tap exists (`flakerimi/homebrew-tap` is aspirational,
> unverified — do not link it as if it's live), no `.deb`/`.rpm`
> packaging, and no artifact signing (Sigstore cosign or otherwise) yet.
> SHA-256 checksums are the one integrity mechanism actually shipping.
> The plan below remains the intended end state.

- **Versioning:** SemVer, `v0.x` until the v1.0 criteria (doc 01) hold.
  Conventional commits → generated changelog (not yet automated —
  release notes so far are written by hand per release).
- **GoReleaser** (planned, not yet adopted) would build `darwin/amd64,
  darwin/arm64, linux/amd64, linux/arm64` (CGO off everywhere — pure-Go
  SQLite pays off here), embed version/commit via ldflags, produce
  tarballs + `checksums.txt`, publish the GitHub Release, update a
  Homebrew tap, and also produce `.deb`/`.rpm` via nfpm (nice-to-have,
  same config) — replacing the hand-cut process above with one `release`
  CI job on tag push.
- **Artifact integrity:** SHA-256 checksums ship today, by hand; Sigstore
  cosign signing is still future work, once the release flow is
  automated.
- **Caddy pinning:** the pinned Caddy version + checksums live in source;
  bumping Caddy = PR that runs the edge test suite.
- install.sh and `basepod upgrade` consuming GitHub Releases (doc 02)
  remains the plan for the automated-upgrade path.

## Documentation plan

- `README.md` — pitch, 3-line install, screenshot, links.
- `docs/` site (later, e.g. VitePress): install guides per platform,
  app-deployment guide, `basepod.yaml` reference, API reference
  (from OpenAPI), plugin author guide, runbooks (backup/restore,
  migration from CapRover — including a captain-definition converter
  note), failure/troubleshooting.
- Every feature PR that changes behavior must touch docs — enforced by
  review checklist, not tooling, initially.

| Milestone | Contents (docs) | Exit criterion |
|---|---|---|
| **v0.1 — walking skeleton** ✅ [shipped](https://github.com/base-al/basepod/releases/tag/v0.1.0) | Repo, CI, installer, `server` boots, Podman+Caddy managed, deploy-by-image via API only (01–05) | Image → running app with HTTPS on a fresh Ubuntu VPS, API-only — met |
| **v0.2 — dashboard** ✅ [shipped](https://github.com/base-al/basepod/releases/tag/v0.2.0) | Dashboard v1 (07): apps CRUD, new-app wizard, live logs, env vars, custom domains, settings tab | A non-CLI user can create, deploy, and manage an app — env, domains, logs — entirely from the browser — met |

| **v0.4 — security hardening + init/manifest + async deploys** 🚧 next milestone | Hardening items surfaced by the v0.3 launch/audit: per-client rate limiting behind the HTTPS dashboard proxy (today's limit is shared across all remote clients — see README's Known issues), container resource limits (CPU/memory caps — none exist today), build-log size caps, security headers, a Go toolchain bump + `govulncheck` wired into CI, and de-colliding the alias/name namespace; plus `basepod init` + a `basepod.yaml` manifest (doc 06 groundwork), async deploys with live CLI build logs (today's CLI deploy blocks synchronously), and a session-management UI + password change (today there is no UI for either — see doc 08 status note) | Security-audit items closed, `basepod init` scaffolds a deployable manifest, CLI deploys stream logs without blocking, admin can change password and see/revoke sessions from the dashboard |

| **v0.6 — git & compose** 🚧 candidate, not yet started | Webhooks, compose, templates catalog (06, 09) | Push-to-deploy demo repo; Postgres template one-click |
| **v0.7 — plugins** | Event bus, webhooks-out, plugin host, 2 first-party plugins (09) | nixpacks plugin deploys a no-Containerfile repo |
| **v0.8 — multi-server** | Agent mode, servers screen, app move (10) — including the `server_id` schema migration doc 10's status note now flags as still-required | 2-server demo: app moved between servers, HTTPS intact |
| **v0.9 — hardening** | Backups, upgrade path tests, docs site, macOS polish | Beta users run it for 30 days without data loss |
| **v1.0** | — | Doc 01 criterion: fresh VPS/Mac → live HTTPS app in <10 min |

Sequencing rationale: every milestone ships something usable end-to-end
(walking-skeleton style), and the riskiest integrations (Podman, Caddy,
rootless networking) are validated in v0.1 before any UI or team
features stack on top.

**Reorder note (v0.2 ⇄ v0.3, this milestone):** the original plan put
"real deploys" (tarball/build pipeline + CLI) right after v0.1, with the
dashboard following in v0.3. That order got flipped user-driven — a
working browser UI was wanted before the CLI/build pipeline, on the
premise that most non-CLI users will judge BasePod by the dashboard
first. v0.2 therefore shipped the dashboard against v0.1's existing
deploy-by-image API (apps, env vars, custom domains, live logs — all
exercised end-to-end in `scripts/e2e-local.sh`, run in CI), and the
tarball/build pipeline + CLI core moves to v0.3. Nothing else in the
roadmap shifts: it was a straight swap of two adjacent milestones, not
a renumbering of the whole plan.

**v0.3 status:** shipped as
[v0.3.0](https://github.com/base-al/basepod/releases/tag/v0.3.0)
(tarball builds, rollback, CLI core, plus the hardening and
dashboard-over-HTTPS work folded in alongside it). The VPS upgrade
rollout is tracked separately, outside this task list.

**Reorder note (v0.4, this refresh):** the table above previously listed
teams (08) as v0.4 and git/compose (06, 09) as v0.5, both "candidate, not
yet started," with the pick between them left open. That's superseded:
v0.3's own release surfaced concrete near-term work (a security audit
finding, plus init/manifest and async-deploy gaps noticed while writing
the v0.3 CLI) that's more urgent than either teams or git/compose, so it
now fills the v0.4 slot as "security hardening + init/manifest + async
deploys." Teams, git & compose, plugins, and multi-server all keep their
existing relative order, just shifted one slot later (v0.5–v0.8) — this
is an insertion, not a re-prioritization of what was already there.

## Risks register

> **Status (v0.3):** refreshed against what actually bit us in v0.1–v0.3
> (per git history), not the speculative list this table used to carry.
> Resolved risks are dropped rather than kept as dead weight.

| Risk | What happened / mitigation |
|---|---|
| Rootless-podman gateway bind failure | The dashboard's original design bound a listener on the rootless network gateway address so Caddy could reach it; that gateway lives inside the rootless netns and is unbindable from the host netns, so it went CI-red with "cannot assign requested address" — and would have exposed the full control-plane API to every container on the `basepod` network anyway. Fixed (commit `79f854c`) by pivoting to a unix socket in a dedicated `data_dir/caddy-sock` directory, bind-mounted only into the `bp-caddy` container — no other container or network peer can reach it. Socket bind failure (macOS, where `podman machine`'s virtiofs mounts don't carry unix sockets across the VM boundary) now warns and disables the dashboard route instead of failing boot. |
| Wrong-arch cached container image on Apple Silicon | `ensureImage()` skipped `PullImage` whenever `ImageExists` reported a cached hit. On an arm64 host with a stray amd64-tagged `caddy:2.10-alpine` already cached (e.g. left over from an earlier `podman build --platform linux/amd64`), the image manifest was never re-resolved for the host arch, so `bp-caddy` started under qemu emulation and crashed. Fixed (commit `02fc1ea`) by making `PullImage` unconditional and adding `podman.Client.ImageArchitecture` as a defensive check that returns an actionable error naming both architectures on mismatch. |
| E2E timeouts on a loaded CI runner | Fixed curl timeouts (5s, 10s) budgeted for an idle runner started failing on `ubuntu-24.04` GitHub-hosted runners under load — a `/deploy` call that pulls an image and polls health synchronously, or a `DELETE` after six build+rollout cycles in the same run, legitimately took longer. Fixed across two commits (`d401b15`, `241002b`) by giving deploy/delete calls a 90s budget instead of the default. Generalizable risk: any newly added e2e step with a tight fixed timeout is a latent flake on a busy runner. |
| Solo-maintainer scope creep | Not yet tested by real pressure, but still the standing mitigation: milestones are strictly cumulative and doc 09's plugin surface is meant to absorb "wouldn't it be nice" features rather than growing core. |
| Podman v5→v6 API drift | A minimum-version gate at boot exists (`internal/podman/client.go`, exercised via `server.checkPodmanVersion`), so a too-old Podman is caught early. Forward-compatibility against a future Podman v6 is still unverified — there is no CI job running against a podman "edge"/prerelease channel. |

Dropped from the previous version of this table (resolved, no longer a
live risk): **"Nuxt UI outside Nuxt friction"** — Nuxt UI shipped and is
in production use (now on v4, see doc 07); the PrimeVue fallback was
never needed. **"`podman machine` flakiness on macOS CI"** — there is no
macOS CI leg at all yet (see Testing strategy above), so this risk
doesn't currently apply; it should be re-added once macOS CI exists.
**"Rootless networking edge cases across distros"** — folded into the
more specific gateway-bind risk above, which is the concrete instance
that actually occurred; the general published-port fallback (doc 04)
mitigation still stands but CI currently runs a single Linux
distro/runner image, not three, so the original mitigation claim was
already overstated.
