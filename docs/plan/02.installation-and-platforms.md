## Supported platforms

| Platform | Arch | Role | Notes |
|---|---|---|---|
| Linux (Ubuntu 22.04+, Debian 12+, Fedora 40+) | amd64, arm64 | **Production** | Any VPS: Hetzner, DigitalOcean, EC2, … — this is the platform CI actually exercises (`ubuntu-24.04` runner, `.github/workflows/ci.yml`'s `e2e` job) |
| macOS 13+ | arm64 (Apple Silicon) | Dev / homelab | Podman runs in `podman machine` VM |
| macOS 13+ | amd64 (Intel) | Dev / homelab | Same as above |

System requirements: Podman >= 4.9 (the actual floor enforced by
`internal/server.checkPodmanVersion` — see doc 03; the historical target
of >= 5.0 was never wired up as a hard gate), ~512 MB RAM for the control
plane, ports 80/443 free (Linux production, unless you remap via
`BASEPOD_HTTP_PORT`/`BASEPOD_HTTPS_PORT`).

Release tarballs are built for all four Linux/macOS × amd64/arm64
combinations (`basepod_v0.3.0_darwin_amd64.tar.gz`,
`..._darwin_arm64.tar.gz`, `..._linux_amd64.tar.gz`,
`..._linux_arm64.tar.gz`, plus `checksums.txt`), so the platform matrix
above is what's actually shipped, not just planned.

## Install methods

### 1. Download a release tarball (primary, today)

```sh
# pick the asset matching your OS/arch from the Releases page
curl -LO https://github.com/base-al/basepod/releases/download/v0.3.0/basepod_v0.3.0_linux_amd64.tar.gz
curl -LO https://github.com/base-al/basepod/releases/download/v0.3.0/checksums.txt
sha256sum --ignore-missing -c checksums.txt
tar xzf basepod_v0.3.0_linux_amd64.tar.gz
sudo install -m 0755 basepod /usr/local/bin/basepod   # or anywhere on your PATH
```

There is no installer script doing this for you yet — no PATH setup, no
checksum verification prompt, no "detect and re-run for upgrade"
idempotency. It's a plain download-and-extract, and the binary's final
location is entirely up to you (the filesystem-layout table below
describes BasePod's own data/config paths, not where the binary itself
must live).

### 2. Build from source

```sh
git clone https://github.com/base-al/basepod
cd basepod
go build -o basepod ./cmd/basepod       # or: make build (builds the dashboard first)
```

This is the path the README's Quickstart and `scripts/e2e-local.sh`
actually use. Requires Go 1.26+ (per `go.mod`); `make build` also needs
Node (to build `web/`) unless you're fine with the committed placeholder
dashboard shell.

### 3. `curl -fsSL … | sh`, Homebrew, and a vanity `get.basepod.sh` domain — **DESIGN-ONLY**

None of `install.sh`, a `flakerimi/homebrew-tap` (or `base-al/homebrew-tap`)
formula, or a `get.basepod.sh` domain exist. The original design for
`install.sh` (detect OS/arch, download+verify the matching release,
install to `/usr/local/bin` or `~/.local/bin`, offer to install Podman,
print "run `basepod setup`") remains the plan for a future release —
nothing about it should be assumed to work today.

## `basepod setup` — first-run, non-interactive today

The **real** command, exactly as implemented
(`internal/server/setup.go`'s `Setup`, flag-parsed in
`cmd/basepod/main.go`'s `newSetupCmd`):

```sh
basepod setup \
  --config ~/.config/basepod/config.yaml \
  --data-dir ~/.local/share/basepod \
  --root-domain apps.example.com \
  --admin-email admin@example.com \
  --admin-password change-me-please
```

It is **not interactive** — there is no prompt-driven wizard, `--flags`
are the only interface, and it does exactly four things, in order: (1)
refuses to run if `--config`'s path already exists, (2) writes
`config.yaml` (just `root_domain` and `data_dir` — see the shape below),
(3) opens/creates the SQLite DB at `<data-dir>/basepod.db` and refuses if
any user already exists, (4) hashes `--admin-password` with argon2id and
creates the superadmin user, then stores `root_domain` as a DB setting
too. If anything fails after the config file is written, `Setup` deletes
it again, so a failed run doesn't leave a half-initialized `config.yaml`
behind.

Everything else the original wizard design below promised —
Podman/socket verification, `subuid`/`subgid` and lingering checks,
Caddy provisioning, port/sysctl handling, and service-file
writing — happens (only partially) elsewhere or not at all:

- **Podman check** happens at `basepod server` boot, not at `setup`
  time: `internal/server.Run` calls `podman.New` + `Ping` + `Version`
  and refuses to boot with an actionable error ("is Podman running? try
  `podman machine start`") if the socket isn't reachable, and enforces
  the version floor described above. There is no `subuid`/`subgid`
  check, no `loginctl enable-linger` automation, and no `podman machine
  init`/`start` automation anywhere in the codebase — do these
  yourself, as the Prerequisites in the README describe.
- **Caddy provisioning** happens at `basepod server` boot too:
  `caddy.Manager.Ensure` (doc 04) pulls the pinned image and creates the
  `bp-caddy` container if it isn't already there. `setup` itself never
  touches Podman or Caddy at all.
- **Ports** — there is no sysctl automation and no interactive port
  prompt. `basepod server` just binds whatever `HTTPPort`/`HTTPSPort`
  it's configured with (env vars, default 80/443) via `bp-caddy`'s port
  mapping; if a rootless Linux install needs `net.ipv4.ip_unprivileged_
  port_start=80`, you set that yourself (see the guidance retained
  below — it's still correct advice, just not automated).
- **Root domain** and **admin account** are the two things `setup`
  genuinely does handle, via the required `--root-domain` /
  `--admin-email` / `--admin-password` flags above — there's no
  `<ip>.sslip.io` fallback logic; if you don't pass a real domain,
  BasePod issues certificates against whatever you passed regardless.
- **Service registration** does not happen — see "Running as a service"
  below for what you write by hand today.
- There's no "print the dashboard URL" step at the end of `setup`; it
  just prints `Setup complete. Start with: basepod server`.

## Running as a service

**DESIGN-ONLY:** `basepod setup` does not write a systemd unit or a
launchd plist, and there is no `--system` flag. What follows is what a
real deployment does by hand today, which BasePod's design still intends
to automate eventually.

### Linux — systemd (rootless, user scope), written by hand

Create `~/.config/systemd/user/basepod.service` yourself:

```ini
[Unit]
Description=BasePod control plane
Wants=podman.socket
After=podman.socket network-online.target

[Service]
ExecStart=%h/.local/bin/basepod server --config %h/.config/basepod/config.yaml
Restart=on-failure

[Install]
WantedBy=default.target
```

```sh
systemctl --user daemon-reload
systemctl --user enable --now basepod.service
loginctl enable-linger "$USER"   # so it survives logout — see below
```

App and `bp-caddy` containers themselves are **not** supervised by a
generated Quadlet unit (none exists — see doc 03); they run under
Podman's own `--restart=always` policy. For those to come back up after
a host reboot (not just a `basepod` daemon restart), enable Podman's own
restart-on-boot unit for the same user:

```sh
systemctl --user enable --now podman-restart.service
```

A `--system`-flag variant that installs to `/etc/systemd/system` and
runs as a dedicated `basepod` user does not exist; if you want that
today, adapt the unit above by hand.

### macOS — launchd — **DESIGN-ONLY, no automation exists**

No launchd plist is generated. The original design (write
`~/Library/LaunchAgents/al.basecode.basepod.plist` with `KeepAlive`,
`RunAtLoad`, tolerate `podman machine` not yet being started) remains
accurate as a description of *future* work, not present behavior. On
macOS today, run `basepod server` in a terminal (or write your own
plist/launch agent by hand) — see doc 03 for the macOS supervision
story generally.

## Filesystem layout

Verified against `internal/config/config.go` and
`internal/server/setup.go`; corrected from the original design where
they differ.

| Purpose | Linux (rootless) | macOS |
|---|---|---|
| Binary | wherever you put it — no fixed install path (see above) | wherever you put it |
| Config | `~/.config/basepod/config.yaml` (`config.DefaultPath()` = `os.UserConfigDir()/basepod/config.yaml`) | `~/Library/Application Support/basepod/config.yaml` |
| Data (SQLite, `secret.key`, `instance.id`, Caddy config/data/socket dirs, build logs) | `~/.local/share/basepod` (if that directory exists), else `$XDG_DATA_HOME/basepod`, else `~/.config/basepod/data` | `~/Library/Application Support/basepod/data` — **not** the same directory as config; note the `/data` suffix the original design omitted |
| Logs | stdout/stderr only — no file or journald integration in code; under systemd these land in the journal because systemd captures a unit's stdout, not because BasePod writes to it | stdout/stderr only; redirect yourself if not running under a supervisor |
| Quadlet units | **does not exist** — no Quadlet generation anywhere (see doc 03) | n/a |

`defaultDataDir()`'s actual resolution order (`internal/config/config.go`)
is worth calling out as a quirk: it checks `$XDG_DATA_HOME` first, then
whether `~/.local/share` *happens to exist* — regardless of platform, so
a macOS machine with a stray `~/.local/share` directory would get the
Linux-shaped path instead of the `Application Support` one. All of this
is overridable via `--config`/`--data-dir` flags or the
`BASEPOD_DATA_DIR` env var (there's no `BASEPOD_CONFIG` env var — config
path is a flag only, see `cmd/basepod/main.go`).

## config.yaml (as implemented)

```yaml
listen: 127.0.0.1:3080     # API+UI; Caddy exposes it publicly
root_domain: apps.example.com
data_dir: ~/.local/share/basepod
podman_socket: ""          # empty = auto-detect (internal/podman.DetectSocket)
http_port: 80
https_port: 443
```

This is the real shape (`internal/config.Config`) — there is no nested
`caddy:`/`podman:` block as the original design sketched; Caddy has no
config-file-level settings at all (its behavior is hard-coded — pinned
image, admin Unix socket — see doc 04), and Podman has just the one
`podman_socket` field. `acme_email` does not exist as a setting anywhere
— Caddy's automatic HTTPS runs with no explicit ACME email configured.
Every field is also overridable by an env var — see the `BASEPOD_*` list
in the status note above.

## Upgrades

**DESIGN-ONLY** — none of this exists:

- `basepod upgrade` (self-update via the GitHub Releases API) — no such
  command.
- Homebrew-aware upgrade detection — no such thing, since there's no
  Homebrew tap.

What **is** real: SQLite migrations run automatically on daemon start
(forward-only, 3 migrations as of v0.3 — doc 05), and the v0.3.0 release
notes document a real, manual upgrade procedure from v0.2.0: back up
`basepod.db`/`secret.key`/`caddy-data`, point DNS at the dashboard
hostname (or set `dashboard_domain` to `off`) before the first v0.3
boot, then replace the binary and restart — expect the `bp-caddy`
container to be recreated once (drift-detected, see doc 04), causing
roughly 10–30 seconds of ingress downtime for all apps while TLS certs
and app containers themselves are untouched.

**v0.4.2 → v0.5 (instance identity, issue #10):** every container BasePod
created before this release carries no `basepod.instance` label — there
was no such thing yet. The first v0.5 boot mints a stable id
(`<data_dir>/instance.id`, see doc 03's "Naming & labels, and instance
identity" section) and *adopts* every existing unlabeled container and
`bp-caddy` whose app slug is already in `basepod.db` — it does not delete
or recreate them just to relabel them; a container only picks up the new
label the next time it's actually redeployed. No special upgrade steps are
needed for the single-instance case (the overwhelmingly common one — e.g.
base.al's v0.4.2 production install). The label only matters once a
*second* BasePod instance is pointed at the same Podman socket (a second
data dir on the same host): each instance's orphan GC and Caddy manager
now refuse to touch a container or `bp-caddy` labeled with a *different*
instance's id, instead of treating it as an orphan to clean up.

## Uninstall

**DESIGN-ONLY** — there is no `basepod uninstall` command. To remove a
BasePod install by hand: stop the service (or the `basepod server`
process), `podman rm -f` every container labeled
`basepod.managed=true`, `podman network rm basepod`, and delete the
data dir and config file yourself.

## Platform-specific risks & mitigations

| Risk | Mitigation |
|---|---|
| Rootless port 80/443 on Linux | Not automated — set `net.ipv4.ip_unprivileged_port_start=80` yourself (`/etc/sysctl.d/99-basepod.conf`), or remap via `BASEPOD_HTTP_PORT`/`BASEPOD_HTTPS_PORT` behind an external LB |
| `podman machine` VM stopped on macOS | Not automated — `basepod server` fails to boot with an actionable error if Podman isn't reachable; start the VM yourself first |
| Old Podman (< 4.9) | `internal/server.checkPodmanVersion` refuses to boot with an actionable error naming the found version |
| Intel Mac vs Apple Silicon path differences | Release tarballs are built for both; CI does not currently run on macOS runners at all (`.github/workflows/ci.yml` is Ubuntu-only) — macOS is unverified by CI today |
| SELinux (Fedora) volume denials | Not applicable yet — BasePod has no per-app declared volumes today (see doc 03); `bp-caddy`'s own bind mounts don't set `:Z`/`:z` labels |

## Acceptance tests (per platform)

**Partially delivered.** `scripts/e2e-local.sh` is exactly this kind of
scripted end-to-end test — `basepod setup --non-interactive`-equivalent
(it always is; there's no interactive mode to opt out of) → `basepod
server` → deploy → `curl https://...` returns 200 — and it runs in CI
(`.github/workflows/ci.yml`'s `e2e` job) on every push/PR. **What's
missing**: it only runs on Linux amd64 (the `ubuntu-24.04` GitHub-hosted
runner); there is no macOS Intel/ARM CI coverage, and no fresh-VM
install-script step (since there's no install script — see above).
