# 02 — Installation & Platform Support

## Supported platforms

| Platform | Arch | Role | Notes |
|---|---|---|---|
| Linux (Ubuntu 22.04+, Debian 12+, Fedora 40+) | amd64, arm64 | **Production** | Any VPS: Hetzner, DigitalOcean, EC2, … |
| macOS 13+ | arm64 (Apple Silicon) | Dev / homelab | Podman runs in `podman machine` VM |
| macOS 13+ | amd64 (Intel) | Dev / homelab | Same as above |

System requirements: Podman ≥ 5.0, ~512 MB RAM for the control plane,
ports 80/443 free (Linux production).

## Install methods

### 1. Curl-pipe script (primary, Linux + macOS)

```sh
curl -fsSL https://raw.githubusercontent.com/flakerimi/basepod/main/install.sh | sh
```

(A vanity domain like `get.basepod.sh` is a **placeholder** — only adopt it
if/when the domain is actually registered.)

`install.sh` responsibilities:

1. Detect OS (`uname -s`) and arch (`uname -m`, normalize `x86_64→amd64`,
   `aarch64/arm64→arm64`). Abort with a clear message on anything else.
2. Download the matching release binary from GitHub Releases, verify its
   SHA-256 against `checksums.txt`, install to `/usr/local/bin/basepod`
   (or `~/.local/bin` when not root and no sudo).
3. Check for Podman; if missing:
   - Linux: instruct (or offer) `apt/dnf install podman` — never install
     packages without an explicit `--yes`-style confirmation.
   - macOS: instruct `brew install podman`.
4. Print next step: `basepod setup`.

The script is idempotent and re-runnable for upgrades.

### 2. Homebrew (macOS, also works on Linux)

```sh
brew install flakerimi/tap/basepod
```

GoReleaser publishes the formula to a `flakerimi/homebrew-tap` repository
on each release (doc 11).

### 3. Manual

Download from GitHub Releases, `chmod +x`, done. Documented for air-gapped
setups.

## `basepod setup` — first-run wizard

An interactive (with `--non-interactive` flags for automation) command that
converts a fresh machine into a BasePod host:

1. **Podman check** — socket reachable? rootless configured? On Linux:
   verify `subuid`/`subgid` entries exist for the user, enable
   `podman.socket` (user unit), and `loginctl enable-linger $USER` so
   rootless services survive logout. On macOS: `podman machine init`
   (with sensible CPU/RAM defaults) + `podman machine start` if needed.
2. **Caddy provisioning** — download the pinned Caddy release for the
   platform into BasePod's data dir (doc 04); BasePod manages this binary
   itself, so no system Caddy package is required or touched.
3. **Ports** — Linux rootless can't bind 80/443 by default. Setup offers
   (a) `sysctl net.ipv4.ip_unprivileged_port_start=80` (recommended,
   written to `/etc/sysctl.d/99-basepod.conf` with confirmation), or
   (b) high ports behind an external LB. macOS: Caddy binds 80/443
   directly (no restriction for the admin user), used for local dev.
4. **Root domain** — ask for the wildcard domain (e.g. `apps.example.com`)
   or fall back to `<ip>.sslip.io` so HTTPS works with zero DNS setup.
5. **Admin account** — create the initial admin user + password.
6. **Service registration** — see below.
7. Print the dashboard URL.

## Running as a service

### Linux — systemd (rootless, user scope by default)

`basepod setup` writes `~/.config/systemd/user/basepod.service`:

```ini
[Unit]
Description=BasePod control plane
Wants=podman.socket
After=podman.socket network-online.target

[Service]
ExecStart=%h/.local/bin/basepod server
Restart=on-failure
[Install]
WantedBy=default.target
```

`--system` flag installs to `/etc/systemd/system` running as a dedicated
`basepod` user instead (still rootless Podman via that user).

### macOS — launchd

`basepod setup` writes
`~/Library/LaunchAgents/al.basecode.basepod.plist` (label mirrors the
maintainer's domain; final reverse-DNS id to be confirmed) with
`KeepAlive=true`, `RunAtLoad=true`, logs to
`~/Library/Logs/basepod/`. Loaded via `launchctl bootstrap gui/$UID`.
BasePod must tolerate `podman machine` not yet being started at login:
retry loop with backoff, and surface "VM starting…" state in the API.

## Filesystem layout

| Purpose | Linux (rootless) | macOS |
|---|---|---|
| Binary | `/usr/local/bin/basepod` or `~/.local/bin` | `/opt/homebrew/bin` or `/usr/local/bin` |
| Data (SQLite, Caddy binary+data, builds) | `~/.local/share/basepod` | `~/Library/Application Support/basepod` |
| Config | `~/.config/basepod/config.yaml` | `~/Library/Application Support/basepod/config.yaml` |
| Logs | journald | `~/Library/Logs/basepod/` |
| Quadlet units | `~/.config/containers/systemd/` | n/a |

All paths overridable via `BASEPOD_DATA_DIR` / `BASEPOD_CONFIG` / flags.

## config.yaml (initial shape)

```yaml
listen: 127.0.0.1:3080     # API+UI; Caddy exposes it publicly
root_domain: apps.example.com
data_dir: ~/.local/share/basepod
caddy:
  admin: 127.0.0.1:2019
  acme_email: ops@example.com
podman:
  socket: ""                # empty = auto-detect
```

Everything else lives in SQLite. Config file is for bootstrap-level
settings only.

## Upgrades

- `basepod upgrade` — self-update: query GitHub Releases API, download,
  verify checksum, atomically replace own binary, restart service
  (systemd/launchd aware). `--check` to only report.
- SQLite migrations run automatically on daemon start (forward-only,
  doc 05).
- Homebrew users upgrade via `brew upgrade`; `basepod upgrade` detects a
  Homebrew-managed install and defers to it.

## Uninstall

`basepod uninstall` prints exactly what will be removed (service unit,
data dir, Caddy, Quadlet units, containers/volumes with `basepod.managed`
label) and requires typed confirmation. `--keep-data` preserves the data
dir. It never touches Podman itself or non-BasePod containers.

## Platform-specific risks & mitigations

| Risk | Mitigation |
|---|---|
| Rootless port 80/443 on Linux | sysctl option in setup; documented LB alternative |
| `podman machine` VM stopped on macOS | health check + auto-start attempt + clear API/UI state |
| Old Podman (< 5.0) on distro repos | version check in setup with distro-specific upgrade instructions |
| Intel Mac Homebrew path differences | detect `/usr/local` vs `/opt/homebrew`; CI covers both arches |
| SELinux (Fedora) volume denials | mount app volumes with `:Z`/`:z` labels; document |

## Acceptance tests (per platform)

Scripted end-to-end: fresh VM/runner → install script → `basepod setup
--non-interactive` → deploy sample app → `curl https://app.<domain>`
returns 200. Runs in CI on Linux amd64/arm64 and macOS Intel/ARM
(doc 11).
