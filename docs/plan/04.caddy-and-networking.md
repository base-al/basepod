# 04 — Caddy & Edge Networking

## Role

Caddy is BasePod's only edge: it terminates TLS on 80/443, serves the
dashboard, and reverse-proxies every app. BasePod fully owns its Caddy
instance — config is generated, never hand-edited.

## Managed Caddy process

- `basepod setup` downloads a **pinned** Caddy release (version in
  BasePod's source, checksum-verified) to `<data_dir>/caddy/caddy`.
  Upgrades of Caddy ship with BasePod releases, tested together.
- BasePod starts/supervises Caddy the same way apps are supervised:
  a Quadlet-style systemd user unit on Linux (running the binary, not a
  container — it must bind host 80/443 and reach the `basepod` network
  via the host gateway), launchd-child on macOS.
- Caddy's storage (certs, OCSP) lives in `<data_dir>/caddy/data` — backed
  up with everything else.

**Why not Caddy-in-a-container:** binding 80/443 rootless plus reaching
container networks gets awkward; a host binary with
`CAP_NET_BIND_SERVICE` (or the sysctl from doc 02) is simpler and keeps
the edge running even during Podman maintenance.

**App upstream reachability:** apps don't publish host ports (doc 03), so
host-Caddy reaches them via each container's IP on the `basepod` bridge.
BasePod resolves the current IP at deploy time and rewrites upstreams on
every deploy/restart (Podman events keep it fresh). Fallback if bridge
routing proves unreliable on some platform (notably macOS, where the VM
boundary intervenes): publish app ports on 127.0.0.1 high ports inside
the host/VM and proxy to those — the Caddy manager hides which strategy
is in use. macOS defaults to the published-port strategy from day one
(VM makes bridge IPs unreachable from the host).

## Config management — admin API

- Desired state lives in SQLite (apps, domains, TLS settings).
- The Caddy manager renders it to a full Caddy JSON config and pushes to
  `POST /load` on the admin API (`127.0.0.1:2019`) — atomic, validated,
  zero-downtime. No incremental patching: full render + load keeps state
  convergent and debuggable (`GET /config/` always shows truth).
- On daemon start: render, compare with running config, load if different.

### Route model per app

```json
{
  "match": [{"host": ["blog.apps.example.com", "www.myblog.com"]}],
  "handle": [{
    "handler": "reverse_proxy",
    "upstreams": [{"dial": "10.89.0.14:8080"}],
    "health_checks": {"passive": {"fail_duration": "10s"}},
    "headers": {"request": {"set": {"X-Forwarded-Proto": ["{http.request.scheme}"]}}}
  }]
}
```

Plus a route for the dashboard: `basepod.<root-domain>` →
`127.0.0.1:3080`. WebSockets work through Caddy's reverse_proxy without
extra config. HTTP/2 + HTTP/3 on by default.

## TLS strategy

| Scenario | Mechanism |
|---|---|
| `<app>.<root-domain>` subdomains | Per-name ACME (HTTP-01/TLS-ALPN) by default; optional **wildcard** cert via DNS-01 when a DNS provider plugin/API token is configured |
| Custom customer domains | **On-demand TLS**: Caddy asks `GET 127.0.0.1:3080/api/v1/internal/tls-ask?domain=X`; BasePod answers 200 only for domains registered to an app — prevents cert-issuance abuse |
| No DNS yet (fresh install) | `<ip>.sslip.io` root domain works with HTTP-01 immediately |
| Local dev (macOS) | Caddy `internal` CA (`*.localhost` domains, auto-trusted via `caddy trust`) |
| Staging/testing | Let's Encrypt staging endpoint toggle to avoid rate limits |

Custom-domain onboarding UX: UI shows the required DNS record (CNAME/A),
polls DNS until it resolves to the server, then flips the domain active —
cert issuance then happens lazily via on-demand TLS on first request.

## Redirects & extras (per-app toggles, stored in DB)

- `www.` → apex (or reverse)
- Force-HTTPS (default on; Caddy does this automatically)
- Basic-auth guard for staging apps (bcrypt hash stored in DB)
- Custom response headers; gzip/zstd on by default

## Failure handling

| Failure | Behavior |
|---|---|
| Caddy process dies | Supervisor restarts it; certs persist on disk, so recovery is seconds |
| Config load rejected (Caddy validation error) | Previous config keeps running; error surfaced on the deployment and in UI; BasePod never leaves the edge broken |
| ACME failure (DNS not propagated, rate limit) | Domain marked `tls_error` with the ACME error in UI; retry with backoff |
| App container unhealthy | Passive health check ejects upstream → Caddy returns 502 page (branded BasePod error page with app status hint) |

## Port strategy summary

- Linux production: Caddy binds 80/443 (sysctl or capability, doc 02).
- Behind an existing LB/proxy: `--http-port/--https-port` overrides and
  documented `trusted_proxies` setting so client IPs survive.
- macOS dev: 80/443 on localhost.
