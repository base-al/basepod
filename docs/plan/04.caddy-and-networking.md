## Role

Caddy is BasePod's only edge: it terminates TLS on 80/443, serves the
dashboard, and reverse-proxies every app. BasePod fully owns its Caddy
instance — config is generated, never hand-edited.

## Managed Caddy process

- BasePod runs Caddy as a container (`bp-caddy`) on the `basepod` network,
  using a **pinned** image (docker.io/library/caddy:2.10-alpine, pulled and
  verified at setup). Upgrades of Caddy ship with BasePod releases, tested
  together.
- Container is created with restart policy `always` (via podman) and labeled
  `basepod.managed=true`. Linux uses Quadlet supervision (same as apps);
  macOS direct supervision via the event loop (doc 03).
- Caddy's storage (certs, OCSP) lives in a bind-mount
  `<data_dir>/caddy-data` → `/data` inside the container — backed up with
  everything else.
- Config management via admin API on a Unix socket inside the container
  (unix//var/run/caddy/admin.sock), not TCP—only `podman exec` reachability,
  no network exposure.

**Why Caddy-in-a-container (not host binary):** running Caddy as a
host binary cannot reach container IPs through the podman-machine VM
boundary on macOS, and a host admin TCP endpoint is a wider security
surface. Container approach mirrors the hardening decision from the
earlier flakerimi/basepod implementation: admin off TCP entirely (Unix
socket only, reachable only via podman exec).

**App upstream reachability:** apps don't publish host ports (doc 03) and
don't need them. Caddy reaches apps by DNS name on the `basepod` network:
each app container gets a network alias `bp-<slug>` (e.g. `bp-blog`),
and Caddy proxies to `bp-<slug>:<port>`. This works identically on Linux
and macOS because the `basepod` network is created with DNS enabled
(aardvark-dns) and Caddy runs on the same network. No VM boundary
routing issues, no published-port fallback needed.

## Config management — admin API

- Desired state lives in SQLite (apps, domains, TLS settings).
- The Caddy manager renders it to a full Caddy JSON config, writes it
  atomically to `<data_dir>/caddy/current.json` (tmp+rename), and reloads
  via `podman exec bp-caddy caddy reload --config /etc/caddy/current.json
  --address unix//var/run/caddy/admin.sock`. Reload is atomic, validated,
  zero-downtime. No incremental patching: full render + reload keeps state
  convergent and debuggable. Bounded retry (5 attempts) tolerates transient
  macOS/virtiofs bind-mount visibility races.
- On daemon start: render, compare with running config, reload if different.

### Route model per app

**As delivered** (`caddy.Render` in `internal/caddy/render.go`) — every
route is `terminal: true` and carries no passive health-check config,
no forwarded-header rewriting, and no per-app options at all beyond the
hostname list and upstream dial address:

```json
{
  "match": [{"host": ["blog.apps.example.com", "www.myblog.com"]}],
  "handle": [{
    "handler": "reverse_proxy",
    "upstreams": [{"dial": "bp-blog:8080"}]
  }],
  "terminal": true
}
```

The richer example this doc originally showed (`health_checks`,
`X-Forwarded-Proto` header injection) is **design-only** — Caddy's own
default reverse-proxy behavior fills some of that gap implicitly (it
already sets `X-Forwarded-For`/`X-Forwarded-Proto` by default), but
nothing here configures passive health-check ejection explicitly.

### Dashboard route (delivered, v0.3)

BasePod's own dashboard gets a route too, prepended first (and also
`terminal: true`, so it takes priority over any app route that might
otherwise match — enforced further by the `internal/api` layer refusing
a hostname collision):

```json
{
  "match": [{"host": ["basepod.apps.example.com"]}],
  "handle": [{
    "handler": "reverse_proxy",
    "upstreams": [{"dial": "unix//run/basepod/api.sock"}]
  }],
  "terminal": true
}
```

The upstream is a Unix socket at `/run/basepod/api.sock` **inside the
bp-caddy container** — bind-mounted from a host directory
(`<data_dir>/caddy-sock/`) that only `bp-caddy` gets mounted into (no
app container does), which is what actually restricts the dashboard API
to Caddy, not a network-reachable TCP address. `internal/server.Run`
creates the real socket file host-side and binds a second HTTP listener
on it, alongside the main `127.0.0.1:3080` listener. The hostname comes
from the `dashboard_domain` setting (`internal/store`): unset
(the default) computes and persists `basepod.<root_domain>` on first
boot; the literal value `off` disables the route entirely (no listener
is even bound); any other value is used as-is. On macOS, `podman
machine`'s virtiofs-shared mounts don't carry Unix sockets across the
VM boundary, so this route is disabled with a logged warning there —
the dashboard stays reachable at `http://localhost:3080` or via an SSH
tunnel instead (see README's "Remote access" section).

WebSockets work through Caddy's reverse_proxy without extra config.
HTTP/2 + HTTP/3 on by default (Caddy's own defaults; nothing
BasePod-specific configures these).

## TLS strategy

**As delivered:** there is no `apps.tls` section in the rendered config
at all (see `caddy.Render`) — every hostname (generated `<app>.
<root_domain>` and custom domains alike) just gets Caddy's own default
automatic-HTTPS behavior for a host-matched route: per-name ACME,
issued lazily on first request. Force-HTTPS is Caddy's own default for
a route with `automatic_https` unconfigured. Nothing below the table is
BasePod-specific configuration — it's what Caddy already does with a
bare host matcher and no `tls` app block.

| Scenario | Mechanism | Status |
|---|---|---|
| `<app>.<root-domain>` subdomains | Per-name ACME (Caddy's own default) | delivered, but as a side effect of no config existing — not selected/tuned by BasePod |
| Custom customer domains | Same per-name ACME as generated subdomains — **no `/internal/tls-ask` on-demand-TLS gate exists** | design-only for the on-demand gate; a custom domain otherwise gets a cert exactly like a generated one |
| Wildcard cert via DNS-01 | — | design-only; no DNS provider plugin/token config exists |
| No DNS yet (fresh install) | `<ip>.sslip.io` root domain — works because it resolves publicly, same as any other domain, not because of dedicated fallback logic | works today only in the sense that any resolvable domain works |
| Local dev (macOS) | Caddy's built-in `internal` CA only kicks in for domains it can't get a public cert for (e.g. `*.localhost`) — again, Caddy's own default, no BasePod config selects it | delivered as a side effect |
| Staging/testing | Let's Encrypt staging endpoint toggle | design-only |

Custom-domain onboarding UX (DNS-record display, resolution polling
before activating the domain) is **design-only** — `POST
/apps/{slug}/domains` (doc 05) just inserts the hostname and applies
routes immediately; there is no polling step or activation gate.

## Redirects & extras (per-app toggles, stored in DB) — **design-only**

None of this exists. The `domains` table (doc 05, migration 00002) has
exactly four columns — `id`, `app_id`, `hostname`, `created_at` — no
`redirect_www`, `basic_auth_hash`, `tls_status`, or `tls_error` columns.
Consequently: no `www.` → apex redirect, no basic-auth guard, no custom
response headers, and no explicit gzip/zstd toggle (Caddy's own
defaults may still apply compression; nothing here configures it
per-app). Force-HTTPS is still effectively on, per the TLS strategy
note above, just not as a stored per-app toggle.

## Failure handling

| Failure | Behavior | Status |
|---|---|---|
| bp-caddy container stops | Podman's `--restart=always` policy restarts it (no BasePod-side supervisor — see doc 03); certs persist via the `<data_dir>/caddy-data` bind mount | delivered |
| bp-caddy has drifted (wrong image/ports/mounts, or stuck `created`) | Detected once at `basepod server` boot (`caddy.Manager.Ensure`'s `driftReason`); the image is confirmed/pulled *before* the old container is torn down, so a pull failure leaves the old container serving rather than leaving zero ingress. **Exercised for real on the v0.2→v0.3 upgrade**, whose new dashboard-socket mount is exactly this kind of drift: expect ~10–30s of ingress downtime for every app while `bp-caddy` is recreated, with TLS certs and app containers themselves untouched (see release notes / doc 02's Upgrades section) | delivered |
| Config reload rejected (Caddy validation error) | `Apply` retries the `podman exec … caddy reload` up to 5 times (100ms backoff) — mainly to ride out a virtiofs bind-mount visibility lag on macOS, not primarily a validation-retry mechanism — and returns an error to the caller (surfaced as a failed deploy/domain-add API response) if all attempts fail. There is **no** UI-visible "config reload rejected" state, and the just-written `current.json` on disk is **not** rolled back to the last-known-good version on a permanent failure — a subsequent full container recreation would start Caddy fresh from that file | delivered (retry+error), design-only (UI surfacing, on-disk rollback) |
| ACME failure (DNS not propagated, rate limit) | No `tls_error` tracking exists (no such DB column — see doc 05); Caddy handles/retries ACME issuance on its own, invisibly to BasePod | design-only |
| App container unhealthy | The deploy engine's own pre-cutover probe (doc 03) keeps a failing new container off the route entirely — a failed deploy never takes the app down. There is no **passive** in-Caddy health check ejecting an already-routed, already-healthy-at-cutover-time upstream that later goes bad, and no branded 502/503 error page — a dead upstream gets Caddy's stock error response | delivered (pre-cutover probe only), design-only (passive ejection, branded errors) |

## Port strategy summary

- The `bp-caddy` container publishes `hostPort → 80` (HTTP) and
  `hostPort → 443` (HTTPS), where `hostPort` defaults to 80/443,
  overridable via `BASEPOD_HTTP_PORT`/`BASEPOD_HTTPS_PORT` environment
  variables.
- Behind an existing LB/proxy: override the port mappings and configure
  documented `trusted_proxies` setting so client IPs survive.
- Works identically on Linux and macOS (no rootless binding complexity
  because the container process is inside the VM on macOS).
