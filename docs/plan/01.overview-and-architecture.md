## Vision

BasePod is an open-source, self-hosted PaaS: the CapRover experience —
"push code, get a running app with HTTPS" — rebuilt on a modern,
daemonless, rootless stack:

- **Podman** instead of Docker/Swarm — rootless containers, no privileged
  daemon, systemd-native supervision via Quadlet.
- **Caddy** instead of nginx — automatic HTTPS, zero-downtime config
  reloads through a JSON admin API, on-demand TLS for customer domains.
- **One Go binary** instead of a stack of containers — installs on macOS
  (Intel & Apple Silicon) and any Linux VPS in one command.

## Comparison to prior art

| | CapRover | Coolify | Dokku | **BasePod** |
|---|---|---|---|---|
| Runtime | Docker Swarm | Docker | Docker | Podman (rootless) |
| Proxy | nginx | Traefik/Caddy | nginx | Caddy (admin API) |
| Control plane | Node.js in container | PHP/Laravel | shell + plugins | Single Go binary |
| macOS server support | no | no | no | yes (dev/homelab) |
| Teams/RBAC | no | yes | no | yes |
| Plugins | one-click apps only | limited | strong | hooks + OCI plugins + templates |

## Goals

1. **One-command install** on macOS (both architectures) and any Linux VPS.
2. **Deploy anything**: an image name, a directory with a Containerfile, a
   git repository, or a compose file.
3. **Automatic HTTPS** for `<app>.<root-domain>` and custom domains.
4. **Team management**: users, teams, roles, API tokens, audit log.
5. **Server management**: single server first; multiple servers behind one
   control plane later (designed for from day one).
6. **Extensible**: lifecycle hooks, container-based plugins, one-click app
   templates.
7. **No mandatory external dependencies**: SQLite embedded, Caddy and
   Podman are the only system requirements.

## Non-goals (v1)

- Kubernetes compatibility or migration tooling.
- Windows hosts (WSL2 may work; untested, unsupported).
- Autoscaling, multi-region scheduling, service mesh.
- Being a CI system — we build images, we don't run arbitrary pipelines
  (plugins can integrate external CI).

## High-level architecture

As shipped in v0.3 — one process (`basepod server`) that talks to Podman
over its libpod REST socket and drives a Caddy **container** (`bp-caddy`,
not a host binary) on the same shared `basepod` bridge network as every
app container:

```
                        ┌─────────────────────────────── VPS / Mac ─┐
                        │                                           │
  developer ── CLI ──►  │  ┌──────────── basepod server ─────────┐  │
  browser ── HTTPS ──►  │  │  REST API /api/v1   embedded Vue UI │  │
                        │  │                                     │  │
                        │  │  ┌────────┐            ┌──────────┐ │  │
                        │  │  │ Podman │            │  Build   │ │  │
                        │  │  │ client │            │ pipeline │ │  │
                        │  │  └───┬────┘            └────┬─────┘ │  │
                        │  │      │        ┌────────┐    │       │  │
                        │  │  ┌───┴────────┤ SQLite ├────┴────┐  │  │
                        │  └──┤            └────────┘         ├──┘  │
                        │     ▼                                ▼    │
                        │  unix://…/podman.sock (libpod REST, v5.0.0)│
                        │     │                                     │
                        │     ▼        "basepod" bridge network      │
                        │  ┌─────┐ ┌─────┐  (aardvark-dns)  ┌───────┐│
                        │  │app A│ │app B│                  │bp-caddy││
                        │  │(bp- │ │(bp- │ ◄── proxied by ─ │(container,│
                        │  │ A)  │ │ B)  │    DNS alias     │unix-socket││
                        │  └─────┘ └─────┘                  │admin API) │
                        │                                   └───┬───┘│
                        │                            host :80/:443   │
                        └───────────────────────────────────────────┘
```

Git-push/webhook-triggered deploys (shown in earlier drafts of this
diagram) are **not implemented** — see doc 06's status note. Caddy's
admin API is reached over a Unix socket *inside* the `bp-caddy`
container via `podman exec` (see doc 04), not a host-bound `:2019` TCP
port.

### Components

| Component | Responsibility |
|---|---|
| **API server** | REST `/api/v1`, session-token auth, SSE streams for logs/build-logs (`internal/api/`) |
| **Dashboard** | Vue 3 + Vite SPA, embedded via `go:embed` (`web/embed.go`), served by the API server's HTTP mux |
| **Podman client** | A hand-rolled libpod REST client over the Unix socket (`internal/podman/client.go`, versioned `/v5.0.0/libpod/...` paths) — **not** `github.com/containers/podman/v5/pkg/bindings`. Creates/starts/stops/removes containers and networks; no Quadlet generation (see doc 03) |
| **Caddy manager** | Owns the `bp-caddy` container's lifecycle (create, drift-detect, recreate); renders desired state to Caddy JSON; reloads via `podman exec bp-caddy caddy reload` against Caddy's Unix-socket admin API (`internal/caddy/`) |
| **Build pipeline** | Turns a tarball upload into a tagged local image via `podman build` (`internal/build/`). Git/image-registry/compose sources are only partially or not yet built — see doc 06 |
| **Store** | SQLite via `modernc.org/sqlite` (pure Go); migrations embedded (`internal/store/migrations/`, 3 so far); no `server_id` column exists yet — the multi-server phase (doc 10) hasn't started |
| **CLI** | Same binary (`internal/cli/`, wired into `cmd/basepod/`); talks to the API, so identical against local or remote servers — `login`, `context`, `apps`, `deploy`, `logs`, `env`, `rollback`, `status` |
| **Plugin host** *(design-only)* | Not started — no `internal/plugin` package exists. Doc 09 remains a roadmap document |

### One binary, several roles

```
basepod server        # run the control plane (daemon)
basepod agent         # (phase 6) run as worker node agent
basepod login|deploy|apps|logs|...   # client commands
```

## Technology choices & rationale

- **Go 1.26+** (per `go.mod`) — static cross-compiled binaries for all
  four platform targets (release tarballs published for
  darwin/linux × amd64/arm64, see doc 02). Podman access is **not**
  through `github.com/containers/podman/v5/pkg/bindings` — `internal/podman`
  is a small hand-rolled libpod REST client instead (see doc 03 for why).
- **SQLite via `modernc.org/sqlite`** — pure Go (no CGO) keeps
  cross-compilation trivial. WAL mode; one writer (the daemon).
- **Caddy's admin API over a Unix socket, reached via `podman exec`** —
  atomic, validated, zero-downtime config swaps; no file templating
  races. Details in doc 04.
- **Podman restart policy `always`, not Quadlet** (Linux and macOS
  alike) — Quadlet generation was designed but never built; today's
  supervision is `podman run --restart=always` plus, on a real VPS, a
  hand-enabled `podman-restart.service` systemd unit and a hand-written
  `basepod.service` user unit (see doc 02). Details in doc 03.
- **Vue 3 + Vite** (no Nuxt UI) — plain Vite SPA, embedded via
  `web/embed.go`. Details in doc 07.

## Repository layout

The tree below reflects what actually exists on disk as of v0.3 — no
`internal/plugin`, no RBAC/PATs in `internal/auth` (session tokens +
password hashing only), no `install.sh`, and no release *workflow* (the
v0.1.0–v0.3.0 tarballs on GitHub Releases were cut by hand — see doc 02).

```
basepod/
├── cmd/basepod/            # main(); cobra commands: server, setup, + CLI client commands
├── internal/
│   ├── api/                # HTTP handlers, router.go, middleware, SSE
│   ├── auth/               # session tokens (sha256), argon2id passwords — no RBAC/PATs yet
│   ├── build/              # tarball build pipeline (gzip/tar validate -> podman build)
│   ├── caddy/              # bp-caddy container lifecycle, JSON render, admin-API exec
│   ├── cli/                # CLI client: login/apps/deploy/logs/env/rollback/status/context
│   ├── config/             # config.yaml loading
│   ├── crypto/             # XChaCha20-Poly1305 secretbox (env var encryption)
│   ├── deploy/             # deploy engine: pull/build, create, probe, cutover, rollback, orphan GC
│   ├── podman/             # hand-rolled libpod REST client (client.go); no Quadlet generation
│   ├── server/             # boot wiring (Run), config load, setup, dashboard listener
│   └── store/              # sqlite, migrations, repositories
├── web/                    # Vue 3 + Vite dashboard, embedded via web/embed.go
├── docs/plan/              # these documents
├── scripts/e2e-local.sh    # end-to-end smoke test, also run in CI
└── .github/workflows/ci.yml # test + e2e jobs; no release/install pipeline yet
```
