# 05 — Data Model & API

> **Status (v0.3):** DELIVERED — the SQLite store
> (`internal/store/store.go`) with 3 migrations
> (`internal/store/migrations/00001_init.sql` through
> `00003_deploy_sources.sql`), session-token auth
> (`internal/auth/token.go`), argon2id password hashing
> (`internal/auth/password.go`), XChaCha20-Poly1305 env-var encryption
> keyed by `<data_dir>/secret.key` (`internal/crypto/secretbox.go`), and
> the real route table in `internal/api/router.go`. **DESIGN-ONLY**:
> teams, RBAC, API tokens (PATs), audit log, plugins, multi-server —
> **none of these tables or endpoints exist**. The schema and endpoint
> map below have been rewritten to match the shipped v0.3 database and
> router exactly; the original (much larger) design is kept below each,
> clearly marked, as the roadmap for docs 08/09/10.

## Store

- SQLite via `modernc.org/sqlite` (pure Go, no CGO), WAL mode,
  `busy_timeout` set; single-writer discipline (the daemon).
- Migrations: embedded SQL files (`internal/store/migrations/*.sql`),
  forward-only, run on daemon start via `github.com/pressly/goose/v3`
  used as a library (`store.Open` calls `goose.Up`) — this part of the
  original design was decided exactly as scoped.
- **Backups — design-only.** There is no `basepod backup`/`restore`
  command and no `VACUUM INTO` snapshot logic anywhere in the codebase.
  The real, documented procedure (README's "Backup" section) is manual:
  copy `basepod.db`, `secret.key`, and `<data_dir>/caddy-data` yourself.

## Schema (as of migration `00003_deploy_sources.sql`)

**This is a small fraction of the originally-designed schema below.**
There is no `server_id` column anywhere (multi-server, doc 10, hasn't
started), and entire tables from the original design don't exist:
`servers`, `teams`, `team_members`, `volumes`, `registries`,
`api_tokens`, `audit_log`, `plugins`. `sessions` and `domains` in
particular are much narrower than designed. The real tables, exactly as
migrated:

```sql
settings       (key PRIMARY KEY, value TEXT)   -- root_domain, dashboard_domain

users          (id, email UNIQUE, name, password_hash /*argon2id*/,
                is_superadmin, created_at)
                -- no disabled_at column

sessions       (id, user_id, token_hash UNIQUE, created_at, expires_at)
                -- no user_agent, ip, or scopes columns — a session is
                -- just "this user, until this time"

apps           (id, slug UNIQUE, image_ref, port, status, created_at, updated_at)
                -- no team_id/server_id/source_kind/git_url/git_branch/
                -- healthcheck_path/instances/cpu_limit/memory_limit —
                -- an app is just a slug + the image it currently runs

deployments    (id, app_id, number /*per-app sequence, UNIQUE(app_id, number)*/,
                image_ref, status /*deploying|healthy|failed*/, error,
                started_at, finished_at,
                source TEXT DEFAULT 'image',        -- added in 00003: 'image'|'tarball'
                build_log_path TEXT DEFAULT '',      -- added in 00003
                trigger_kind TEXT DEFAULT 'api')      -- added in 00003: 'api'|'rollback'
                -- no triggered_by_user_id, git_sha, or a "queued"/
                -- "building"/"rolled_back"/"superseded" status —
                -- DeployBuild marks the app "deploying" for the whole
                -- build+rollout, not just the rollout half

domains        (id, app_id, hostname UNIQUE, created_at)
                -- no kind, tls_status, tls_error, redirect_www, or
                -- basic_auth_hash columns

env_vars       (id, app_id, key, value_encrypted, is_secret,
                UNIQUE(app_id, key))
                -- this table matches the original design as-is
```

**Secrets at rest:** `env_vars.value_encrypted` is encrypted with a data
key stored in `<data_dir>/secret.key` (generated on first use, see
`internal/crypto.LoadOrCreateKey`) using XChaCha20-Poly1305 — this part
matches the original design exactly. Session tokens are hashed with
SHA-256 (`bp_sess_` prefix, 24 random bytes — `internal/auth.
NewSessionToken`); there is no separate API-token (`bp_pat_`) scheme, so
that half of the original "hash discipline" bullet doesn't apply yet.

### Original design (teams/RBAC/multi-server/audit/plugins) — kept as roadmap, not built

```sql
servers        (id, name, kind /*local|remote*/, address, agent_token_hash,
                status, last_seen_at, created_at)

teams          (id, slug UNIQUE, name, created_at)
team_members   (team_id, user_id, role /*owner|admin|member|viewer*/,
                PRIMARY KEY(team_id, user_id))

volumes        (id, app_id, name, container_path, created_at)

registries     (id, team_id, server, username, password_encrypted)

api_tokens     (id, user_id, name, token_hash, scopes, last_used_at,
                expires_at, created_at)

audit_log      (id, at, user_id, api_token_id, team_id, action,
                resource_kind, resource_id, detail_json, ip)

plugins        (id, name UNIQUE, version, source_ref, enabled,
                config_json, installed_at)
```

These carry no migration, no store methods, and nothing in
`internal/api` references them — they describe docs 08/09/10's
still-unstarted scope, not anything partially built.

## API

- Base: `/api/v1`, JSON — matches the design. **No OpenAPI spec
  exists** (no `api/openapi.yaml`, no `/api/v1/openapi.json` route,
  no spec-vs-handler CI check) — the dashboard and CLI are both
  hand-written directly against `internal/api`.
- Auth: **Bearer token only** — `Authorization: Bearer <session
  token>`. There is no cookie-based session for the dashboard (it also
  uses the Bearer header, stored in browser storage) and no CSRF token
  handling, since there's no cookie to forge. `bp_pat_`-prefixed
  personal access tokens don't exist — every token in the system today
  is a login session token (`bp_sess_` prefix). One deliberate
  exception: the log-streaming routes (`/apps/{slug}/logs` and
  `/apps/{slug}/deployments/{number}/log`) also accept the same session
  token via `?access_token=`, because a browser's native `EventSource`
  can't set request headers — verified to be rejected on every other
  route (`scripts/e2e-local.sh` asserts `?access_token=` against
  `/apps` gets 401).
- Errors: `{"error": {"code": "...", "message": "..."}}` — matches the
  design. Login-only rate limiting is real (10 attempts/minute per
  client IP, `internal/api`'s `rateLimiter`) but nothing else is
  rate-limited.
- Team scoping — **design-only**. There are no teams, so no
  `X-Basepod-Team` header or `?team=` parameter is read anywhere; every
  authenticated user sees every app.

### Endpoint map — real routes only (`internal/api/router.go`)

```
POST /api/v1/auth/login                          # public
GET  /api/v1/auth/me                              POST /api/v1/auth/logout
GET  /api/v1/system

POST   /api/v1/apps                     GET /api/v1/apps
GET    /api/v1/apps/{slug}              DELETE /api/v1/apps/{slug}
POST   /api/v1/apps/{slug}/deploy               # body: {"image": "ref"} or {} (redeploy current image)
POST   /api/v1/apps/{slug}/deploy/tarball       # gzipped-tar body, own body-size cap
POST   /api/v1/apps/{slug}/rollback             # body: {"number": n}
GET/PUT /api/v1/apps/{slug}/env                 # PUT is bulk-replace; secrets write-only, masked on read
GET/POST /api/v1/apps/{slug}/domains            DELETE /api/v1/apps/{slug}/domains/{id}
GET    /api/v1/apps/{slug}/logs                 # SSE, ?follow&tail=N, also accepts ?access_token=
GET    /api/v1/apps/{slug}/deployments/{number}/log   # SSE while building, plain text once finished; also accepts ?access_token=
```

That's the complete route table as of v0.3 — every route below this
line is **design-only** (present in the original scope, not in
`router.go`):

```
GET  /api/v1/apps/{slug}/deployments             # no separate list endpoint — GET /apps/{slug} embeds the deployments array instead
POST /api/v1/apps/{slug}/start|stop|restart      # no lifecycle endpoints beyond deploy/rollback/delete
GET  /api/v1/apps/{slug}/stats                   # SSE — no stats streaming (doc 03)
POST /api/v1/apps/{slug}/exec                    # WebSocket interactive shell
GET/POST/DELETE /api/v1/apps/{slug}/volumes      # no volumes table (doc 03)
GET/PATCH /api/v1/apps/{slug}                    # PATCH doesn't exist — an app's mutable fields are only reachable via deploy/env/domains

POST /api/v1/setup                               # `basepod setup` is a local CLI/filesystem operation (doc 02), not an HTTP endpoint
GET/POST/DELETE /api/v1/teams …                  # no teams
GET/POST/DELETE /api/v1/tokens                   # no PATs
GET  /api/v1/audit                               # no audit log
GET/POST /api/v1/registries                      # no registries table
GET  /api/v1/events                              # no SSE event bus beyond per-app logs/build-logs
POST /api/v1/webhooks/git/{app-uuid}/{secret}    # no git webhooks (doc 06)
GET  /api/v1/internal/tls-ask                    # no on-demand TLS gate (doc 04)
GET/POST /api/v1/plugins …                       # doc 09
GET/POST /api/v1/servers …                       # doc 10
```

### Streaming

SSE for logs and build-logs is delivered (works through Caddy's
reverse proxy without extra config, including the remote dashboard
route). SSE for stats/events, and WebSocket for `/exec`, are
design-only — see the route tables above.

## Auth details

- Passwords: argon2id — matches the design (fixed parameters
  `m=65536,t=3,p=2`, PHC-style encoded string, bounds-checked on verify
  so a crafted hash string can't crash or resource-exhaust the process).
- Sessions: **fixed 30-day expiry from creation, not a sliding window**
  — nothing extends `expires_at` on use. `POST /auth/logout` deletes the
  current session row outright (real, and covered by
  `scripts/e2e-local.sh`), but there is no "list my sessions" or
  "revoke session N" UI/endpoint — logout can only end the session
  making the call.
- PATs — **design-only**. No `bp_pat_` scheme, no scopes, no `api_tokens`
  table (see schema above); every credential in the system is a login
  session token.
- First-run: matches the design in spirit, but via the CLI, not an API
  route — `basepod setup` (doc 02) creates the superadmin directly
  against the store; there is no `/setup` HTTP endpoint to lock after
  first use, because it was never an HTTP endpoint.
- 2FA (TOTP) — design-only; no `totp_secret` column exists.
