# BasePod v0.3 — Hardening + Remote Dashboard + Real Deploys

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close v0.2's security/ops debt (dashboard reachable over HTTPS remotely, server hardening, session revocation, drift reconciliation), then ship the "real deploys" milestone: tarball upload → server-side image build → deploy, build logs, rollback, and the `basepod` CLI client commands.

**Architecture:** No new subsystems — extends existing packages. Dashboard exposure works by BasePod adding a second listener on the podman-network gateway address and rendering a Caddy route for `basepod.<root_domain>` to it (the container can reach the gateway; the public internet cannot). Builds use the libpod build endpoint with an uploaded tar context, streamed to per-deployment build logs on disk + SSE. CLI reuses the REST API with a context file (`~/.config/basepod/cli.yaml`).

**Tech Stack:** unchanged (Go stdlib + existing deps; no new Go deps expected except possibly none — tar handling is stdlib). Frontend gains `vitest` as a dev-dep for unit tests.

## Global Constraints

- Everything from v0.1/v0.2 plans still binds: module path, labels (`basepod.managed/app/deployment`), naming (`bp-<slug>-<n>`), error envelope, conventional commits, NO AI attribution, CGO off, vet/gofmt clean, tidy go.mod, secrets never in logs/errors, single-binary integrity.
- The live production VPS (base.al) upgrades to v0.3 at the end — every schema/config change must migrate cleanly from a v0.2.0 data dir (additive goose migrations only; new settings default sensibly when absent).
- Dashboard exposure must never make plain-HTTP secrets transit the public internet: API keeps loopback + gateway binds only; public access is exclusively via Caddy TLS.
- Build contexts are untrusted input: size-capped, extracted nowhere (streamed to podman as tar), never executed on the host.

### Task 1: Server hardening batch

**Files:** Modify `internal/server/server.go`, `internal/api/router.go` (+ tests).

- `http.Server`: `ReadHeaderTimeout: 10s`, `IdleTimeout: 120s`; NO global WriteTimeout (SSE); document why in a comment.
- `http.MaxBytesReader` middleware: 1 MiB default on JSON routes; the future tarball route is exempted by design (its own cap in Task 6). 413 → error envelope `request_too_large`.
- Login rate limiter: evict stale per-IP entries (janitor goroutine or lazy sweep on insert; keep it simple), bounding the map.
- Bearer prefix case-insensitive (`strings.EqualFold` on the scheme token) — closes the v0.1 deferred minor.
- `GET /apps/{slug}/logs?tail=0` → clamp to 1 (closes deferred minor).
- Podman version gate at boot: parse `GET /version` (libpod) — require ≥ 4.9, else fail with actionable error.
- Tests: 413 on oversized JSON body; lowercase `bearer` accepted; rate-limiter eviction (time-injectable); version-gate rejection with a fake daemon.

### Task 6: Tarball deploys — upload + build pipeline

**Files:** Create `internal/build/build.go`; Modify `internal/podman/client.go` (BuildImage), `internal/deploy/deploy.go`, `internal/api/apps.go` (upload route), `internal/store` (migration 3: deployments gain `source` TEXT DEFAULT 'image', `build_log_path` TEXT DEFAULT '') (+ tests).

- `POST /api/v1/apps/{slug}/deploy/tarball` — body: raw gzipped tar (Content-Type application/gzip), cap 256 MiB (its own MaxBytesReader). Context must contain `Containerfile` or `Dockerfile` at root (validated by streaming the tar index BEFORE building; reject otherwise 422 `no_containerfile`).
- `podman.BuildImage(ctx, tag string, context io.Reader, logSink io.Writer) error` — libpod `/build?dockerfile=&t=` POST with tar body; stream response JSON (`{"stream":...}` lines) to logSink; surface `{"error":...}`.
- Build pipeline in `internal/build`: orchestrates: save upload to a temp spool file (data dir `builds/` — `trash`-safe cleanup), tag `localhost/basepod/<slug>:<n>`, write build log to `<data>/apps/<slug>/builds/<n>.log`, then hand off to the existing deploy engine with the built image ref (engine gains `DeployBuilt(ctx, app, imageTag, deployment)` or reuse Deploy with a pre-created deployment — design the seam cleanly; deployment row created BEFORE build so the log path is addressable).
- Deployment JSON gains `source` + `has_build_log`.
- `GET /apps/{slug}/deployments/{n}/log` — SSE (reuse the demux-free path: build logs are plain lines on disk; stream file + follow while building) or plain text when finished (`?follow=0`). Keep v1 simple: while building, SSE tail; after, full text response.
- Global build concurrency: 2 (semaphore); per-app: 1 (mutex map).
- Tests: tar-index validation (missing Containerfile 422), build error surfaces, build log written, happy path with fake runtime BuildImage.
