# BasePod v0.4 — Security Hardening + Zero-Config Deploys

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Close every High and most Medium findings from the v0.3 security audit, then make deploys zero-config (`basepod init` + `basepod.yaml`) and asynchronous (live build logs in the CLI, no more minutes-long blocking HTTP requests).

**Architecture:** No new subsystems. Security work touches `internal/api` (rate limiting, headers, stream tokens), `internal/podman` + `internal/deploy` (resource limits, naming), `internal/build` (log caps, tar linkname validation). Zero-config work adds manifest parsing in `internal/build` + a new `basepod init` command in `internal/cli`. Async deploys convert the tarball endpoint from "block until healthy" to "202 + deployment number", with clients following the existing build-log SSE stream.

**Tech Stack:** unchanged; Go toolchain bumped to ≥1.26.5; `govulncheck` added to CI.

## Global Constraints

- All prior constraints hold (module path, labels, naming, error envelope, conventional commits, NO AI attribution, CGO off, vet/gofmt/vitest clean, tidy go.mod).
- Must migrate cleanly from a live v0.3.0 data dir (additive goose migrations only).
- Security fixes must ship with a regression test that fails without the fix.
- The production VPS (base.al) upgrades at the end; container-limit defaults must not break the two running apps (whoami, the site).

### Task 1: Per-client rate limiting behind the proxy (audit H1)

**Files:** `internal/api/auth.go`, `internal/api/router.go`, `internal/server/server.go` (+ tests)

- `api.New` gains a flag/field marking which listener a request arrived on. Implementation: the server wraps the unix-socket listener's handler with a middleware setting a context value `trustedProxy=true`; the loopback listener does not.
- `clientIP(r)`: when `trustedProxy` is set, take the LAST hop of `X-Forwarded-For` (Caddy appends the real client); otherwise `RemoteAddr` host. Never trust XFF on the loopback listener.
- Successful logins do NOT consume a bucket slot (only failures count).
- Add a global ceiling (e.g. 100 failed logins/min across all IPs) so a distributed flood still can't wedge the box, but a single IP can't lock everyone out.
- Tests: XFF honored only on the trusted listener; spoofed XFF ignored on loopback; successful login doesn't consume; per-IP isolation (attacker IP exhausted, admin IP still allowed); global ceiling trips.

### Task 2: Container resource limits + hardening flags (audit H2)

**Files:** `internal/podman/types.go`, `internal/podman/client.go`, `internal/deploy/deploy.go`, `internal/store` (migration 4: apps gain `memory_limit_mb INTEGER NOT NULL DEFAULT 512`, `cpu_limit REAL NOT NULL DEFAULT 1.0`, `pids_limit INTEGER NOT NULL DEFAULT 512`), `internal/api/apps.go` (expose in app JSON + PATCH), web (settings tab fields) (+ tests)

- `CreateSpec` gains MemoryLimitBytes, CPUQuota (period 100000), PidsLimit, plus fixed hardening: `no-new-privileges`, drop `NET_RAW`.
- Map onto libpod `resource_limits` (`memory.limit`, `cpu.quota`/`cpu.period`, `pids.limit`) and `cap_drop`/`security_opt` in specGen — VERIFY field names against the live libpod API before coding (read-only curl allowed).
- Defaults applied to new apps; existing apps get the migration defaults. Settings tab lets the admin raise/lower per app; validation (min 64 MiB, max = host RAM guess or unbounded with explicit 0).
- Tests: spec carries the limits; zero means unlimited; migration defaults apply to pre-existing rows; UI round-trip.

### Task 3: Build-log caps, log pruning, app-directory cleanup (audit H3)

**Files:** `internal/build/build.go`, `internal/podman/client.go` (BuildImage sink), `internal/deploy/deploy.go` (prune hook), `internal/api/apps.go` (delete path) (+ tests)

- Wrap the build-log file in a limiting writer: cap 32 MiB, then append `\n--- build log truncated at 32 MiB ---\n` and stop writing (build continues; the stream is what's capped).
- Prune build logs alongside built images: keep logs for the retained deployments only.
- `handleDeleteApp`: after RemoveApp + DeleteApp, `os.RemoveAll(<dataDir>/apps/<slug>)` (guarded: path built from validated slug, must be inside dataDir).
- Tests: writer truncates and annotates; prune removes only non-retained logs; delete removes the app dir and nothing above it.

### Task 4: Namespace de-collision + reserved slugs (audit M1)

**Files:** `internal/deploy/deploy.go`, `internal/api/apps.go`, `internal/caddy/render.go` (+ tests, e2e)

- Change the network alias scheme so app aliases can never collide with container names: alias becomes `app-<slug>` (containers stay `bp-<slug>-<n>`); upstreams become `app-<slug>:<port>`.
- Reject reserved slugs at creation: `caddy`, `basepod`, plus anything matching `^bp-` or `^app-`.
- MIGRATION CONCERN: existing deployed apps carry the old alias. On boot, reconcile: any running app container missing the new alias is recreated? NO — too destructive. Instead: routes render BOTH aliases as upstreams? No — a route has one upstream. Decision: the alias is set at container creation, so the new scheme applies to the next deploy; boot reconciliation detects containers with only the legacy alias and keeps rendering `bp-<slug>` upstreams for them (store a per-app `alias_scheme` column, migration 4, default 'legacy' for existing rows, 'v2' for new deploys). Document the transition; drop legacy support in v0.6.
- Tests: collision case (app `foo-2` vs app `foo`) routes correctly under the new scheme; reserved slugs 422; legacy apps keep working until redeployed.

### Task 5: Security headers, stream tokens, listen guard, tar linkname (audit M2/M4/M5/M6)

**Files:** `internal/server/server.go`, `internal/api/router.go` + `logs.go`, `internal/config/config.go`, `internal/build/build.go`, `web/src/lib/sse.ts` (+ tests)

- Security-headers middleware on the root handler: CSP `default-src 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, HSTS (only when served over the dashboard route — set unconditionally is fine since plain-HTTP loopback ignores it; document).
- Stream tokens: `POST /api/v1/stream-token {scope:"logs"|"build", slug, deployment?}` → short-lived (5 min) single-purpose token; SSE routes accept ONLY stream tokens via `?access_token=`; session tokens rejected there. Frontend `sse.ts` mints one before connecting and re-mints on reconnect.
- `listen` validation: refuse non-loopback bind addresses unless `BASEPOD_ALLOW_PUBLIC_LISTEN=1`, with a loud error explaining the dashboard route is the supported public path.
- tar validation: reject `TypeSymlink`/`TypeLink` entries whose `Linkname` is absolute or escapes the context.
- Tests for each; e2e asserts a session token is now 401 on the logs route while a minted stream token works.

### Task 8: `basepod.yaml` manifest + `basepod init`

**Files:** `internal/manifest/manifest.go` (new), `internal/build/build.go` (read manifest from the tar), `internal/deploy/deploy.go` (apply port/health/env defaults), `internal/cli/commands.go` (`init`), docs (+ tests)

- Manifest schema (v1 subset of doc 06): `name`, `port`, `healthcheck.path`, `build.containerfile`, `build.args`, `env` (non-secret defaults), `resources.memory`/`cpus`. Unknown keys → warning, not error.
- Build pipeline: if `basepod.yaml` is present at the tar root, parse it; app port/healthcheck/resources are set from it when the app doesn't already override; build args passed to podman build.
- `basepod init`: interactive-ish scaffold — detect the project type (package.json / go.mod / requirements.txt / index.html) and write a `basepod.yaml` plus, if absent, a starter `Containerfile` for that stack (honest, minimal, commented). `--force` to overwrite; prints next steps.
- Tests: manifest parse matrix (valid, unknown keys, bad types), build applies port from manifest, `init` scaffolds per detected stack (table test over fixture dirs), `init` refuses to clobber without `--force`.

### Task 9: Async deploys + live CLI build logs

**Files:** `internal/api/apps.go`, `internal/deploy/deploy.go`, `internal/build/build.go`, `internal/cli/commands.go`, `web/src` (+ tests, e2e)

- Tarball endpoint returns **202 + deployment JSON** immediately after the upload is spooled and validated; the build+rollout runs in a background goroutine bounded by the existing semaphore, with a detached context (not the request's).
- Deployment status transitions remain the source of truth; add `GET /apps/{slug}/deployments/{n}` for polling.
- CLI `deploy`: upload → get deployment number → stream the build log via SSE (stream token) → poll status until terminal → exit code from status. `--detach` to skip following.
- Dashboard: unchanged behavior (it already polls + streams), but remove the long-request assumption.
- Server shutdown: in-flight background deploys get a grace period; on hard stop the deployment is marked failed at next boot (add a boot sweep: any deployment left `deploying` with no running container → mark failed).
- Tests: 202 shape; background completion updates status; CLI follows to success and to failure; boot sweep marks orphaned in-flight deployments failed.
