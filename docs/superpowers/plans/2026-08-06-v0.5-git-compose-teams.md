# BasePod v0.5 — Git Push-to-Deploy + Compose

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the two deploy sources doc 06 still lists as design-only — git push-to-deploy (per-app webhook with HMAC verification, server-side shallow clone into the existing build pipeline, private-repo tokens, connect-repo UI with recent deliveries) and compose support (translate the documented `compose.yaml` subset into one BasePod app per service on the shared network) — plus the `GET /apps/{slug}/stats` CPU/mem SSE stream doc 07 promises sparklines for, and a real OpenAPI spec with a CI conformance check. Teams/RBAC (doc 08) is **deliberately deferred whole to v0.6** — see the scope decision below.

## Scope decision: what is v0.5 and what is v0.6 (read first)

The candidate pile for this milestone was git + compose + teams + stats + exec + OpenAPI. That is two full milestones pretending to be one, and it will not land. The split:

**v0.5 (this plan):** git push-to-deploy, compose, named-volume + `replace`-strategy substrate (compose needs it for stateful services), stats SSE + sparkline, OpenAPI spec + conformance check.

**v0.6 (next):** teams/RBAC **whole** — users/teams/membership, `authorize()` + route→capability table + matrix tests, invitations, scoped PATs, audit log (all of doc 08) — plus the `/exec` terminal and the CLI `domains`/`exec` wrappers.

Why teams defers rather than splits:

1. **Teams is the single largest cross-cutting migration on the roadmap.** Today there is exactly one superadmin and every resource is unscoped: `apps`, `domains`, `env_vars`, `deployments` (and, after this milestone, `git_sources`, `git_deliveries`, `volumes`) all need a `team_id` (directly or via their app), every one of the ~30 handlers needs an authorization call, and the SSE/stream-token and CLI paths need scoping too. There is no "minimum coherent slice" that is honest: teams without enforcement is theater, enforcement without teams is dead code, and PATs without scopes are just a second session-token scheme. Doc 08's own design (single `authorize()` from a route→capability table, matrix-tested) argues for doing it in one sweep, not dribbled across milestones.
2. **Doing teams *after* git/compose makes the v0.6 migration simpler, not harder.** Every resource in the system today — and every resource this plan adds — is uniformly unscoped, so v0.6's backfill is one uniform rule ("everything belongs to the bootstrap `default` team"). Landing teams first would instead force this milestone's two new subsystems to be built team-aware from day one, roughly doubling both tasks' surface while delivering zero user-visible value to the actual production instance (base.al), which has one operator.
3. **Git webhooks are the natural continuation of the work landing right now.** Issue #2 (async deploys, `feat/async-deploys`) converts the tarball pipeline to 202-and-background exactly because a deploy must not hold an HTTP request open — which is precisely what a webhook receiver needs. Building webhooks immediately on top of that machinery, while it is fresh, is the highest-leverage sequencing available.
4. **`/exec` belongs with RBAC.** Doc 08's permission matrix gates "Exec into containers" at admin+. Shipping exec in v0.6 alongside `authorize()` means an interactive root shell over WebSocket never exists ungated, even for a release.
5. The roadmap's original "git & compose" milestone also listed a **templates catalog** ("Postgres template one-click"). That stays deferred — doc 09 frames templates as plugin-surface material, and this milestone's volume + internal-service substrate is the prerequisite it was missing. Task 12 amends the roadmap accordingly.

**Why the in-milestone order is git → compose → stats/OpenAPI:** git is first because it reuses the async-deploy machinery landing now and is the top missing PaaS workflow (the roadmap's own exit criterion: "push-to-deploy demo repo"). Compose is second because it consumes git's groundwork — the shared source packer (Task 1) for per-service build contexts and the same async orchestration — and because its volumes/replace substrate (Task 6) is self-contained. Stats and OpenAPI come last: both are small, independent, and droppable to v0.6 without unravelling anything if the milestone runs long — the reverse is not true of any earlier task.

**Architecture:** No new subsystems beyond two leaf packages. Git support is `internal/gitsource` (shallow clone via the host `git` binary, resolved by absolute path like `podman` is, token passed via `GIT_ASKPASS` pointing back at the basepod binary — never in argv) feeding the **existing** build pipeline: clone → pack with the shared tar packer → the same gzipped-tar path `DeployBuild` already validates (Containerfile check, symlink rejection, manifest parsing, size caps all inherited for free). The webhook receiver is one unauthenticated route with its own security battery, which only ever deploys the *stored* repo config — the payload can trigger and filter, never steer. Compose is `internal/compose` (hand-rolled parser for the documented subset over the existing `yaml.v3` dep — not the compose-go library) translating to N apps keyed by `(project, service)`, deployed in `depends_on` order through the same async pipeline. Stats is one new libpod client method streamed out as SSE under the existing stream-token auth. OpenAPI is a hand-written spec + a `chi.Walk` conformance test so it cannot drift.

**Tech Stack:** unchanged — no new Go dependencies. Git operations shell out to the host `git` (availability checked at boot, warn-only; same pattern as the absolute-path `podman` resolution from v0.4). Compose parsing uses the existing `gopkg.in/yaml.v3`. The sparkline is hand-rolled inline SVG — no chart library (doc 07's uPlot/chart.js suggestion deferred until a real charts screen exists).

## Global Constraints

- All prior constraints hold: module path `github.com/base-al/basepod`, labels (`basepod.managed/app/deployment`), naming (`bp-<slug>-<n>`, alias `app-<slug>` v2 scheme), error envelope `{"error":{"code","message"}}`, conventional commits, **NO AI attribution**, CGO off, `go vet`/`gofmt`/vitest clean, tidy go.mod, single-binary integrity.
- **Additive goose migrations only.** Production (base.al) runs v0.4.0 with migrations `00001`–`00006` applied; this plan's migrations start at **`00007`**. Before writing the first one, check the merged `feat/async-deploys` work (issue #2) for any migration it added and renumber upward — same collision that forced the stream-tokens renumber in v0.4.
- **Build on issue #2, do not duplicate it.** Assume async deploys have landed: tarball deploys return 202 + deployment JSON, `GET /apps/{slug}/deployments/{n}` exists for polling, background deploys run on a detached context under the build semaphore, and a boot sweep fails orphaned `deploying` rows. Rebase onto it; the webhook and compose orchestration call the same async entry point.
- The live VPS upgrades to v0.5 at the end: every change must come up cleanly on a v0.4.0 data dir (new tables empty, new columns defaulted, no compose/git config present → behavior identical to v0.4).
- **The webhook route is unauthenticated by design.** Its security battery is non-negotiable: constant-time signature/token comparison (`hmac.Equal`/`subtle.ConstantTimeCompare`), 1 MiB body cap, per-hook rate limiting, per-app coalescing under flood, clone URL **only ever from stored config** (never from the payload — no SSRF surface), `https` scheme allowlist, clone timeout + post-clone size cap, and responses that don't oracle hook existence or secret validity beyond generic status codes.
- Cloned repos and compose files are untrusted input: clones go through the exact same tar validation as uploads; compose parsing is strict, and unsupported keys **warn loudly, never silently drop** (doc 06's ruling).
- Secrets never in logs or error strings: webhook secrets and repo deploy tokens are sealed with the same AAD-bound XChaCha20-Poly1305 scheme as env values; deploy tokens are write-only through the API (masked on read); tokens never appear in process argv, git output, or delivery records.
- Every task ends CI-green (`test` + `e2e` jobs) before the next begins.

### Task 3: `internal/gitsource` — shallow clone into a build context

**Files:** Create `internal/gitsource/gitsource.go` (+ tests); Modify `cmd/basepod/main.go` (hidden askpass subcommand), `internal/server/server.go` (boot-time git availability check, warn-only).

**Interfaces:**

```go
gitsource.New(gitPath string, opts Options) *Cloner   // gitPath resolved once at boot like podman's; Options{Timeout (5m), MaxRepoBytes (512 MiB), AllowedSchemes ([https]; tests inject file://)}
(*Cloner).Fetch(ctx, url, branch, token string) (gzTar io.ReadCloser, headSHA string, err error)
```

- `Fetch` mechanics: validate scheme against the allowlist (`http` only via `BASEPOD_GIT_ALLOW_HTTP=1`, logged loudly — for LAN Gitea); `git clone --depth 1 --single-branch --branch <b> --no-tags <url> <tmpdir>` under `exec.CommandContext` with the Options timeout; `GIT_TERMINAL_PROMPT=0` always. Token transport: `GIT_ASKPASS` points at the basepod binary's hidden `internal-git-askpass` subcommand, which prints `$BASEPOD_GIT_TOKEN` from the child's env — the token never appears in argv, in the URL, or in `.git/config`. Read `headSHA` via `git -C <tmpdir> rev-parse HEAD`. Enforce `MaxRepoBytes` by walking the checkout post-clone (clear error naming the cap); strip `.git`; pack via `tarpack.PackToTempFile` + gzip; caller streams it into the normal build path. Temp dirs removed in a defer.
- Boot check in `server.Run`: resolve `git` (config override `git_path`, else PATH); missing → **warn** "git deploys disabled until git is installed", not fatal — image/tarball deploys are unaffected. `Fetch` returns a typed `ErrGitUnavailable` the API maps to 503 `git_unavailable`.
- Tests: fixture repos created with the real git binary in `t.TempDir()` (CI runners and dev Macs have git), cloned via `file://` with the test-injected scheme; branch selection; missing-branch error surfaces git's stderr (sanitized — assert no token-bearing strings); size-cap rejection; timeout (ctx cancel kills the child); askpass subcommand prints env token and nothing else; scheme rejection.

### Task 4: Git config API + manual deploy-from-git

**Files:** Modify `internal/api/router.go`, create `internal/api/git.go`, modify `internal/deploy/deploy.go` (+ tests); Modify `internal/cli/commands.go` (`basepod git` verbs).

**Interfaces:**

```
PUT    /api/v1/apps/{slug}/git      {url, branch, token?}   → git source JSON incl. webhook_url + secret
GET    /api/v1/apps/{slug}/git       → same, token masked ("set"|"") — secret IS returned (see below)
DELETE /api/v1/apps/{slug}/git       → 204
GET    /api/v1/apps/{slug}/git/deliveries?limit=20

```

- `PUT` on first connect generates `hook_id` (24 random bytes, hex) and the secret (32 hex chars), seals both (`AAD = appID|"git_secret"` / `|"git_token"`); re-PUT keeps hook_id/secret stable unless `{"rotate_secret":true}`. Webhook URL in responses: `https://<dashboard_domain>/api/v1/webhooks/git/<hook_id>` (fall back to a relative path when no dashboard domain is set, with a `warnings` entry).
- Deliberate deviation from strict write-only: the **webhook secret is readable** via GET — the operator must paste it into GitHub/GitLab/Gitea settings, possibly repeatedly. The **deploy token is write-only** (masked like secret env values). Both documented in doc 06's refresh (Task 12).
- URL validation at PUT time: parseable, scheme in allowlist, host non-empty. No DNS/SSRF gymnastics needed beyond that: the URL is set by an authenticated operator who can already deploy arbitrary containers — the SSRF property that matters (webhook payloads can't steer the clone) lives in Task 5.
- `POST /deploy/git`: load source config → `gitsource.Fetch` → hand the gzTar to the **async** deploy path from issue #2 (202 immediately after the clone-and-spool succeeds; clone errors are synchronous 4xx/5xx so the operator gets actionable feedback while testing the connection). Deployment rows: `source='git'` (the `source` column is free TEXT — no migration for the new value), `trigger_kind='api'`. Where does the commit SHA live? Manual deploys write no delivery row, and smuggling it into `image_ref` or a delivery lookup would be dishonest bookkeeping. Decision: `deployments` gains a `git_sha TEXT NOT NULL DEFAULT ''` column — added in migration 00007 (owned by Task 2's file, used first here) and surfaced in deployment JSON.
- CLI: `basepod git connect <app> --url --branch [--token]`, `basepod git status <app>` (shows webhook URL + last deliveries), `basepod git disconnect <app>`, `basepod deploy --git <app>` triggering the manual endpoint and following the build-log SSE like a tarball deploy does post-issue-#2.
- Tests: connect/read/rotate/disconnect round-trip (secret stable across re-PUT, rotates on demand); token masked on GET; manual deploy happy path with a fake Fetch; `git_unavailable` mapping; clone failure → 502 `git_clone_failed` with sanitized message.

### Task 5: Unauthenticated webhook receiver

**Files:** Create `internal/api/webhook.go`; Modify `internal/api/router.go` (own route group: no `requireAuth`, own 1 MiB body cap), `internal/api/git.go` (shared trigger helper) (+ tests).

**Interfaces:** `POST /api/v1/webhooks/git/{hookID}` — public.

- Resolution: unknown/malformed `hookID` → generic 404 `not_found` (same envelope as any missing route — no oracle). Everything below happens only after the hook resolves.
- **Verification, constant-time, before any parsing beyond headers:** read body (capped 1 MiB via its own `http.MaxBytesReader`; over-cap → 413, delivery `error`). GitHub: `X-Hub-Signature-256: sha256=<hex>` — compute HMAC-SHA256 over the raw body with the unsealed secret, compare via `hmac.Equal`. Gitea: `X-Gitea-Signature: <hex>` — same HMAC compare (Gitea also sends `X-Hub-Signature-256`; accept either). GitLab: `X-Gitlab-Token: <secret>` — no HMAC exists; `subtle.ConstantTimeCompare` against the secret. None present → 401. Invalid → 401 `invalid_signature`, delivery recorded as `invalid_signature` (capped: at most the prune window — floods of forgeries can't grow the table unboundedly beyond keep=50).
- **Event + branch filter:** `X-GitHub-Event`/`X-Gitea-Event`/`X-Gitlab-Event` — `ping` → 200, delivery `ignored_event`; anything but push → 202, `ignored_event`. Push payload: parse only `ref` and head SHA (`after` / `checkout_sha`); `refs/heads/<branch>` must equal the configured branch else 202 `ignored_branch`; branch-deletion pushes (`after` all-zeros) → 202 `ignored_event`. The payload is **never** a source of the clone URL — the stored `git_sources.url` is the only thing fetched.
- **Rate limit + flood coalescing:** per-hook fixed-window limit (30/min, reusing the existing `rateLimiter`) → 429, delivery `rate_limited`. Coalescer (small struct in `internal/api`, per-app mutex map like the builder's): at most one deploy running + one pending per app; a push arriving while one runs sets/overwrites the pending marker (delivery `coalesced`) and a single follow-up deploy fires when the running one finishes — a flood of N pushes yields at most 2 deploys, last SHA wins.
- Accepted pushes: 202 `{"status":"queued"}`, delivery `deployed` linked to the deployment row (`trigger_kind='webhook'`, `source='git'`, `git_sha` set). The clone itself runs inside the detached background deploy (a webhook response must not wait a 5-minute clone); clone failures land on the deployment row as `failed` + delivery updated to `error`.
- Tests (the security battery, each one failing without its guard): valid GitHub/Gitea/GitLab verification; forged signature 401 + constant-time compare used (assert `hmac.Equal` by construction/review, plus wrong-length sigs rejected); oversized body 413; unknown hook 404 indistinguishable from unknown route; branch filter; ping; deletion push; rate limit trips; coalescing under 5 rapid pushes → ≤2 deploys, latest SHA; payload with a different repo URL in it still clones the stored URL (fake cloner asserts).

### Task 7: `internal/compose` — parse + translate the documented subset

**Files:** Create `internal/compose/compose.go` (+ tests).

**Interfaces:**

```go
compose.Parse(r io.Reader) (*File, []string /*warnings*/, error)
compose.Plan(f *File, project string, existing PlanContext) (*Plan, error)  // PlanContext: existing apps by (project,service), taken aliases
type Plan struct{ Project string; Services []ServicePlan; Warnings []string }
type ServicePlan struct{ Name, Slug, Image string; Build *BuildRef; Port int; Internal bool; Env map[string]string; Volumes []VolumeRef; DependsOn []string; Action string /*create|update*/; Warnings []string }
```

- Supported keys (doc 06's ruling: direct translation, **not** `podman kube play`): `services.<name>.image`, `build` (string context or `{context, dockerfile, args}`), `environment` (map and `K=V`-list forms), `volumes` (named `vol:/path` only), `depends_on` (list form; `condition` map form accepted with a warning — ordering is what we honor), `expose`, plus top-level `name` (project) and top-level `volumes` (names validated against services' usage).
- Semantics: `expose` present → routed app, `Port = expose[0]` (more than one → warning naming the extras). No `expose` → **internal service**: no Caddy route, no probe target (`Port = 0`) — how a compose `db` stays private. `ports` (host publishing) is **unsupported → warning** telling the user routing happens via Caddy domains/expose. **Bind mounts are rejected with an error** (host filesystem access, not merely unsupported). Every other unknown key — `networks`, `restart`, `deploy`, `healthcheck`, `${VAR}` interpolation, profiles, extends — collects an explicit warning naming the key and service; **nothing is ever silently dropped**.
- Naming + collision rules: service names must be valid DNS labels and must not match `^bp-|^app-`, `caddy`, `basepod` (they become raw network aliases — the v0.4 alias-namespace fix must not be reopened). Slug = `<project>-<service>`, validated against the existing slug rules incl. the 32-char cap (error naming offenders). The bare service-name alias is claimed globally on the shared network: `Plan` errors if another project's service (or any existing app) already holds that alias — first come, first served, spelled out in the error.
- Tests: table-driven parse matrix (both env forms, both build forms, unsupported-key warnings each named, bind-mount error, bad YAML); plan matrix (create vs update actions, alias conflict, slug too long, reserved service name, expose/internal split, depends_on cycle detected here → error).

Task 5's webhook trigger and Task 8's orchestrator both sit on issue #2's async entry point — if that branch's final shape differs from the issue sketch (202 contract, polling endpoint, boot sweep), Tasks 4/5/8 adapt to what actually merged, not to this plan's assumption. - **Alias-namespace regression risk (v0.4 finding M1):** compose's bare service-name aliases deliberately re-enter the flat DNS namespace that fix cleaned up. The guards are Task 7's reserved-pattern rejection (`^bp-`, `^app-`, `caddy`, `basepod`) and the global first-claim conflict check — both must be matrix-tested before Task 8 wires containers up.
- **Two writers, one volume:** the `replace` strategy exists precisely so compose database services never run two containers against one named volume during a rollout. Task 8 force-setting `replace` for volume-bearing services (with a warning) is load-bearing correctness, not polish; if it's dropped, redeploying a compose Postgres corrupts data.
- **Secret-handling deviations, made consciously:** webhook secret is readable via GET (operators must paste it into forge UIs); deploy token stays write-only; both AAD-sealed at rest; the askpass-env scheme keeps tokens out of argv/`ps`. GitLab's header-token scheme has no HMAC — that's GitLab's protocol, not a corner cut; the constant-time compare is the available rigor there.
- **What this milestone deliberately does not do:** SSH deploy keys (https+token covers the forges' recommended CI patterns), GitHub App/commit-status integration (doc 09 plugin candidate), compose `${VAR}` interpolation/`networks`/`healthcheck` keys (warned, not dropped), manual volume CRUD, apps-list sparklines, `/exec`, and all of teams — each has a stated landing slot above rather than silent omission.
